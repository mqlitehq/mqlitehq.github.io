# 生产运维

本手册对应 `main`，包含尚未发布的改动。最新受支持版本为 v0.4.2（端口 6754，schema token 7）；
运行该二进制时，请使用 [v0.4.2 运维手册](https://github.com/mqlitehq/mqlite/blob/v0.4.2/docs/operations.md)。
尤其是，下述保留租约的启动与本地维护、协同 broker 关停，以及调整后的托管 Receiver 行为
尚未发布；参见 [CHANGELOG.md](../CHANGELOG.md#unreleased)。
v0.3.3 已撤回且不受支持；其公开产物和准确镜像仅供取证或兼容性检查，不得部署。
v0.4.2 保留 v0.4.0 对 v0.3.3 的撤回声明。
从 v0.3.2 或其他 schema-5 版本升级时，必须按下述流程使用全新数据库。
运行时管理的访问密钥要求 v0.3.1；v0.3.0 只支持配置 token。
统一的 `Observe` 与已配置的监控凭据要求 v0.3.2。
从 v0.2.0 升级会同时改变默认端口（8080）和 schema token（2）；
替换 broker 之前，请先遵循[升级与回滚](#upgrade-and-rollback)。
安装见[部署](deployment.md)，指标定义和告警见[可观测性](observability.md)。

v0.4.2 是基于 v0.4.1 的同 schema 补丁。作用范围覆盖整个 broker 的 `listen` 密钥
可创建／更新订阅和测试过滤器；完整清单和删除仍属于 `manage` 操作。
明确优先接受 HTML 的浏览器根路径请求会进入已启用的控制台，curl 和 JSON 客户端仍获得
服务发现响应。协议契约不变，无需重建数据库或迁移指标。
替换二进制期间仍须暂停客户端活动，并避免新旧 broker 重叠运行。

## 运行边界

- 每个数据库只运行一个活跃 broker。本地文件只有一个 MQLite 所有者和一个写入连接；
  还可以额外打开一个只读观测连接。其他进程应使用 HTTP 客户端。
  不支持两个 broker 共享同一个 Turso 数据库：启动恢复以旧所有者已经停止为前提。
  不要让滚动替换中的新旧进程同时访问同一数据库。
- 本地存储应使用持久化的本地文件系统或附加块存储卷，并具备正常的刷盘语义。
  SQLite WAL 不适用于网络文件系统。容量应覆盖峰值积压、WAL、临时操作、备份和日志保留。
- 生产环境中，已确认提交必须在操作系统故障或断电后仍保留时，使用 `MQLITE_SYNC=FULL`。
  默认 `NORMAL` 可防护进程崩溃，但断电可能丢失近期提交。
  `FULL` 仍依赖存储栈正确执行刷盘；SIGKILL 测试不能模拟断电。
- 设置稳定的 `MQLITE_TOKENS`，在入口终止 HTTPS，并让 broker 位于代理之后或私有网络中。
  配置 token 拥有管理员权限；运行时密钥可限制整个 broker 范围内的发送或监听权限。
  没有逐队列角色。凭据应存于权限受限的环境配置／密钥文件。
- 消费者必须具备幂等性。重启、响应丢失和恢复旧快照都可能重复执行已经产生外部副作用的工作。
  在文档规定的保留窗口内重试时，应复用稳定的 `MessageID`／正文、接收 `AttemptID`
  和完全相同的结算请求；不要将 HTTP 超时视为写入失败的证明。
  发送去重默认关闭：依赖 `MessageID` 前，先配置覆盖重试期间的正数队列去重窗口，
  并保持元数据、TTL 和定时时间不变。重复发送不会延长窗口。
  结算回执 30 分钟后到期，重放不会续期；资源删除或固定订阅到期可更早结束重放。
  对账期限必须超过这些边界时，应用应保留自己的账本。
  Peek-Lock AttemptID 仅在保存记录尚未到期、且保存批次的所有消息仍拥有有效租约时才能重放。
  broker 重启会保留这些未到期租约与 token；租约到期或结算后，broker 会使陈旧响应失效，
  在新领取中安全地重新判断符合条件的工作，不会返回已经失效的所有权。
  仅当原始 Receive 响应未被观察到时，才复用该 AttemptID。
  一旦收到响应，保留其 token，并在后续 Receive 调用使用新的 AttemptID；
  部分缓存批次失效时，其他仍有效的租约会特意留给原调用方，避免产生并发投递。
  计划替换 broker 时，停机时间应短于剩余租期；或者先停止新接收，让处理函数先完成结算。
  在停机期间到期的租约遵循正常重投／最后一次投递进 DLQ 的规则。

接下来三项边界适用于 v0.4.0 及后续版本。
v0.3.2 提供完整、仅含 active 项的 `ListSubscriptions` 操作，但没有队列／订阅删除、
具备生命周期感知的订阅分页清单、订阅容量设置或固定订阅 TTL。

- 由一个控制方独占负责队列或订阅删除和同名重建。暂停生产者和消费者活动。
  除非有意永久丢弃，否则使用仅允许空资源删除的默认方式；force 还会丢弃可能已经产生外部效果的
  锁定工作。接受删除的事务会将资源移入 `deleting` 并开始清理。
  继续清理时，该标记保留名称；规模较小的删除也可能在同一次提交中完成。
  已接受删除的订阅立即退出主题扇出。重建前确认名称已消失。
  对不确定结果进行对账期间，继续保留名称；替代资源已经存在后，绝不重放旧删除请求。
- 将默认 10,000 个 active-plus-deleting 订阅上限视为元数据安全上限。
  应用需要更严格的边界时，选择更低限制。按预期活跃数量测量扇出延迟、数据库增长和观测成本；
  每个匹配订阅都会生成一份额外消息副本。
  稳定回复订阅配合 `correlation_id` 的扩展性优于每请求创建订阅。
  必须使用临时订阅时，使用全局唯一、仅用一次的名称，并限制创建／删除速率，使有界清理能够跟上。
- 将固定订阅 TTL 视为遗忘清理时的兜底。截止时间是绝对时间，到期即授权丢弃所有保留状态；
  流量与过滤器修改不会续期。正常完成时显式删除，错开大规模到期波峰；
  容量规划应包含未消费正文的字节数，以及到期后清理所需时间。
- 保持 broker 主机 UTC 时钟同步，并对大幅时间跳变告警。
  订阅截止时间、定时投递、消息 TTL 和租约到期均使用该时钟。
  时钟向前跳可能使截止时间提前到来；向后跳可能延迟尚未持久化标记为 `deleting` 的订阅到期。
  将绝对截止时间与 Status 或 Observe 的 `server_time_ms` 对比；
  不要将浏览器时钟或缓存的 `sampled_at_ms` 作为生命周期参考。
- 将全局队列 gauge 视为采样监控数据。在单个 broker 进程内，`Observe`、`/metrics`
  和控制台会共享约 10 秒的数据，并暴露原始 `sampled_at_ms`；操作需要当前排空判断时，
  使用新鲜的逐队列 `Stats`。刷新本身很慢时，其耗时会进一步增加消息 gauge 的可能年龄。
  常规抓取间隔保持 15 秒或更长，除非实测负载证明有必要更频繁探测。
  即使只刷新一次缓存，仍需扫描保留中的消息；深积压时可能消耗 CPU、存储带宽和 WAL checkpoint 余量。

上线前，先选择并记录应用的恢复目标：可接受的快照年龄（RPO）、恢复时间（RTO）、积压年龄
和容量限制。使用有代表性的数据测量恢复耗时。
仅有备份命令成功，不等于完成恢复测试。

## Broker 优雅关停

下面的协同关停和保留租约的重启契约要求尚未发布的 `main`；已安装的 v0.4.2 broker
不提供这些保证。它也不会排空应用消费者。取消 `Receiver.Run` 会取消在途处理函数的上下文。
`Run` 仍会等待处理函数与结算返回，但不会在取消前给予处理函数自然完成的宽限期。
被中断的投递可能消耗投递机会，或在达到配置上限时进入 DLQ。
计划停止消费者且必须完成其工作时，应先在应用层停止新工作并排空，再取消消费者。

`mqlite serve` 将首个 SIGINT 或 SIGTERM 视为优雅关停请求。
它停止接受新的 HTTP 连接，并关闭内部 Receive 禁止新领取屏障。
在领取轮次之间等待的调用会被唤醒，收到 `200` 和空消息列表；
因此，托管 Receiver 可在 broker 重启后重新连接。调用方主动取消仍返回 `499`。
停止与领取准入共享同一个原子边界：关停前已获准的轮次保留调用方上下文，
返回其真实消息或错误；之后的轮次不会开始数据库操作。
只有已经完成过一次确认空结果轮次的调用，才收到 `200` 唤醒响应。
在首次轮次前被屏障挡住的 Receive 获得带 `Retry-After` 的 `503 unavailable`
（启用 CORS 时暴露该头），并保留 AttemptID，以便重放之前已经提交、但响应丢失的领取。
其他已获准请求保留其上下文，并得到最多 25 秒用于排空；broker 不会仅为唤醒 long-poll
而中断在途 Send 或结算。无法完成的处理请求（例如客户端上传请求正文时停滞）会消耗该排空预算。
随后，broker 关闭引擎操作准入，等待已获准数据库工作和后台维护结束，关闭数据库，再释放本地文件锁。
引擎或诊断日志关闭失败会使命令以非零状态退出。

broker 启动会保留 active 资源上尚未到期的 Peek-Lock 租约、隔离 token 和投递计数。
资源生命周期和消息 TTL 仍然有效。跨越短暂 broker 重启仍在运行的远程处理函数，
因而可以在重连后继续续锁或完成同一次投递；重启本身不会造成消息重复，
也不会额外消耗一次投递机会。停机时间达到 `locked_until` 时，启动恢复（或租约回收器）
会应用通常的到期规则：未达到投递上限时返回 active，最后一次投递则进入 DLQ。
锁时长和部署宽限期应确保计划重启通常能在剩余租期内完成。
测量从停止旧 broker 到新 listener 就绪的完整间隔，包含数据库打开和 schema 检查。
默认租约为 30 秒；实测远程存储重启及续锁／结算延迟需要更多余量时，应配置更长租约。
托管 Go 客户端的续锁与结算重试预算也有上限：Complete/Abandon 终结结算清理的总预算
最多五秒，包含首次请求和所有重放。因此，在租约到期前恢复是保住特定处理函数结算的必要条件，
但不是充分条件；重试预算耗尽后，不会在 broker 稍后恢复时自动继续。
持有有效 token 也不能保证外部副作用只发生一次。

停机 broker 的数据库可以由本地 CLI 检查或维护命令打开，而不撤销尚未到期的投递：
每次 Open 默认都保留活跃租约。本地文件仍要求单一所有者，因此先停止 broker，
绝不并发打开同一 DB。程序内服务必须在 `Serve` 之前指定 `WithBrokerMode`，
选择其关停与生命周期契约。单进程嵌入式所有者只有在确认所有旧处理函数都已结束时，
才能使用 `WithReclaimUnexpiredLeases`；这种显式接管会使活跃 token 失效，
并可能将最后一次投递移入 DLQ。

观察到第一个信号后，会在优雅关停开始前恢复操作系统的正常信号行为。
因此，第二个 SIGINT 或 SIGTERM 会立即强制终止进程。
只有在愿意放弃剩余 HTTP 请求处理与清理、而不再等待时，才使用这种升级手段：
第二个信号之后，进程无法再执行额外结算或关闭代码。
SQLite 事务仍然以原子方式恢复。已提交且尚未到期的 Peek-Lock 租约在下次 broker 打开数据库时保留；
超过截止时间后，可重新投递，或在最后一次投递时进入 DLQ。
应用副作用可能已经发生，因此仍须具备幂等性。
Ctrl-D 是终端输入 EOF，不是关停信号；broker 不读取 stdin。

Receive gate 是在领取轮次之间等待的调用所使用的禁止新领取屏障。
已获准的领取事务保留调用方请求上下文，可能返回在关停开始前已经提交的工作。
如果连这一在途边界也必须严格控制，应在计划替换 broker 前先暂停消费者活动。

平台外层终止宽限期应大于：

```text
25s HTTP drain + Engine.Close duration + log and process-exit margin
```

`Engine.Close` 会有意等待已获准工作结束，不会用不安全的超时在写入可能仍运行时释放所有权。
因此，平台外层截止时间是最终硬上限。仓库的 `docker-compose.yml` 设置
`stop_grace_period: 40s`；普通 Docker 默认只等待 10 秒，可能在刻意停滞的请求
仍处于 25 秒 HTTP 排空阶段时发出 SIGKILL。
Kubernetes 常见默认终止宽限期是 30 秒，最坏 HTTP 排空结束后仅剩约 5 秒供引擎关闭和进程退出；
应配置至少 40 秒，实测远程存储关闭需要更多时间时还应增加。
Turso/libSQL 替换仍须保持单活，先停再启；这些关停行为不意味着重叠运行 broker 就安全。

## 消费者停止与主机中断

这些边界描述尚未发布的 `main` 与两个 Go 客户端的托管 `Receiver.Run`。
SDK 不会安装进程信号处理器。宿主应用决定 SIGINT/SIGTERM、stdin EOF 和平台宽限期
如何影响其上下文；`Consumer.Shutdown` 以及先停止准入、再排空的 API 均未实现。
Ctrl-D 通常产生 stdin EOF，不是进程信号，也不会自动取消上下文；`mqlite serve` 不读取 stdin。

| 事件 | 当前行为与必需措施 |
|---|---|
| Broker 在剩余租期内停止并重启 | 活跃 Receiver 会重试，并可复用持久化的 token。续锁和结算还必须在各自重试预算内完成。保持单个活跃 broker，不要取消 Receiver 的控制上下文。 |
| Broker 停机持续到租约到期 | 原 token 无法续锁或产生新的结算效果。未达到 `MaxDeliveryCount` 时返回 active；达到上限时进入 DLQ。保留的精确请求回执仍可确认此前已提交的结算。 |
| 应用取消 `Run` | Receive 重试停止，处理函数／续锁上下文立即取消。`Run` 仍等待工作器和清理结束。处理函数返回 `nil` 请求 Complete；返回非 nil 请求在新上下文中执行最多五秒的 Abandon，除非最终续锁失败已使结算不安全。取消不会给处理函数宽限期。 |
| 处理函数、错误回调或自定义传输忽略取消 | 等待这些工作结束时，关停可能一直阻塞。上下文取消是协作式的，不是终止 goroutine，也不是硬返回截止时间。 |
| 应用调用 Close 方法 | `Receiver.Close` 不执行操作；`Client.Close` 仅释放 SDK 拥有的空闲 HTTP 连接。两者都不会取消活跃 Run。`Embedded.Close` 等待的是已获准数据库工作，不是应用处理函数。关闭客户端或引擎前，先取消并等待 Receiver 返回。 |
| Broker 仍可用时，消费者被杀死、SIGSTOP 或容器暂停 | 被杀死的进程无法结算；被暂停的进程无法续锁。到期租约遵循通常的重投／DLQ 规则。即使旧 token 已被隔离，恢复后的处理函数也可能已经造成外部变更。 |
| Broker 被杀死 | 没有 HTTP 排空或清理保证。本地事务原子恢复，默认启动保留仍有效的租约。提交前后响应丢失时，调用方必须对账（例如通过精确请求回执）；进程死亡本身不能证明回滚。`:memory:` 在进程退出时丢失所有状态。 |
| 屏幕关闭或锁屏；机器休眠、冻结或断电 | 仅关闭屏幕或锁屏不会向进程发信号，也不会取消其上下文；操作系统可能另行暂停主机。主机休眠或故障期间，不要假定仍会服务、续锁或清理；恢复时 broker 时钟上的截止时间可能已过。SIGSTOP、容器暂停／重启和 SIGKILL 是进程故障模型，不是主机休眠或断电行为的证明。 |

计划停止消费者时，应安排应用级准入控制，让工作先结算后再取消；
也可以使用生命周期由应用自行控制的显式 Receive 循环。
被中断的最后一次投递即使没有业务处理函数失败，也可能进入 DLQ。
未对账外部副作用前，不要反复重启或 redrive 不具备幂等性的处理函数。

成功的 Send 确认回执表示事务已按配置的存储契约提交，
不表示消费者的外部工作已经完成。本地 `NORMAL` 防护进程崩溃；
断电耐久性要求 `FULL` 及正确执行刷盘的存储栈。
Turso/libSQL 的耐久性属于远程服务契约，不是本地容器测试证明的设置。
恢复测试必须明确实际覆盖了哪一种故障模型。

## 启动与例行检查

固定二进制校验和或镜像 digest，并记录其源码提交、Go 版本、MQLite 版本和 schema token。
演练与实际运行使用相同配置，尤其是耐久性、消息大小限制和 DLQ 保留设置。

`GET /healthz` 是进程存活检查，其处理器不查询存储。
使用带身份验证的 `AdminService/Status` 检查后端（`ping_ms >= 0`）和生命周期时钟
（`server_time_ms`），再用专用 canary 队列验证完整写入／消费／结算循环。
读取成功不能证明磁盘仍有空间可供写入。

```bash
export MQLITE_ENDPOINT=http://127.0.0.1:6754
# Set MQLITE_TOKEN from your secret manager; do not paste it into shell history.
mqlite status --output json
mqlite create-queue ops-canary
mqlite send ops-canary "canary-$(date -u +%s)"
mqlite receive ops-canary
mqlite metrics ops-canary --output json
```

CLI `receive` 在打印消息之后会完成消息，除非指定 `--no-ack`。
最终 canary 队列总量必须为零。每次只运行一个 canary 消费者，且与业务流量分离。
周期性 canary 应将返回正文与自己发送的身份进行比对；消息异常或缺失时应失败。

监控进程／容器重启、内存、剩余磁盘、DB 加 WAL 大小、最近备份年龄、RPC 错误和队列年龄／深度。
积压 gauge 与完成计数器的区别见[可观测性](observability.md)。
在保留策略移除死信之前检查其内容；保留策略提供有界故障缓冲，不是归档。
预留新备份以及长时间读取期间 WAL 增长的空间。

## 密钥轮换

为每个生产者、消费者或管理员使用单独的受管理密钥。
`manage` 密钥可以签发或撤销密钥，包括其他管理员密钥；`send` 或 `listen` 密钥不可以。
控制台管理要求 `manage`；只读指标抓取器或监控视图使用单独配置的 `MQLITE_MONITOR_TOKENS`。
这些凭据不依赖密钥数据库。参见[监控入门栈](observability.md)和[云集成指南](observability-cloud.md)。
通过 `mqlite key create` 创建受管理密钥，将客户端切换到替代密钥，
然后执行 `mqlite key revoke --id <old-id>`。变更持久化在数据库中，无需重启 broker 即可生效。
撤销会拒绝新的身份验证尝试；已经授权的请求可以完成。
由其他密钥签发的密钥是独立的，因此撤销签发者不会撤销其签发的密钥。

已配置管理员凭据的轮换仍采用 `MQLITE_TOKENS=old,new`，重启 broker，
切换客户端／抓取器，然后移除旧配置 token，再次重启。
每次替换期间暂停客户端活动，并在恢复流量之前验证 canary。
这里显式配置的 token 即使与之匹配的数据库密钥已到期或撤销，也仍然是管理员；
要撤销静态授权，必须移除该配置。保留一份已配置管理员凭据用于恢复，
并避免将密钥留在命令历史中。

## 一致备份

这些流程适用于本地 SQLite 文件。Turso 备份和时间点恢复属于远程服务；
应演练该提供方的恢复流程，并在切换期间保持只有一个活跃 MQLite 所有者。

像保护在线数据库一样保护备份：其中包含消息正文、属性、受管理密钥摘要／权限／撤销信息，
以及所有嵌入式发件箱业务表。
在数据库故障域之外保留经过验证的副本，同时保留匹配的二进制／镜像身份及恢复所需配置。
明文凭据另行存储。恢复快照也会恢复当时的密钥状态：较新的密钥可能消失，
快照之后撤销的密钥可能重新有效。重新开放客户端流量前，使用已配置管理员凭据检查密钥元数据，
对备份后状态发生变化的凭据进行撤销或替换。

### 在线快照

使用只读连接访问在线源数据库，并使用新的目标文件名：

```bash
umask 077
MQ_DB=/var/lib/mqlite/mq.db
MQ_BACKUP_DIR=/var/backups/mqlite
mkdir -p "$MQ_BACKUP_DIR"
MQ_SNAPSHOT="$MQ_BACKUP_DIR/mq-$(date -u +%Y%m%dT%H%M%SZ).db"
sqlite3 -readonly "$MQ_DB" '.timeout 10000' "VACUUM INTO '$MQ_SNAPSHOT'"
test "$(sqlite3 -readonly "$MQ_SNAPSHOT" 'PRAGMA integrity_check')" = ok
test -z "$(sqlite3 -readonly "$MQ_SNAPSHOT" 'PRAGMA foreign_key_check')"
test "$(sqlite3 -readonly "$MQ_SNAPSHOT" \
  'SELECT COUNT(*) FROM messages m LEFT JOIN queues q ON q.name=m.queue WHERE q.name IS NULL')" = 0
sqlite3 -readonly "$MQ_SNAPSHOT" "SELECT value FROM meta WHERE key='schema_version'"
sha256sum "$MQ_SNAPSHOT" > "$MQ_SNAPSHOT.sha256"
```

运行命令时启用错误检查（脚本中使用 `set -e`）。失败或被中断的快照不是备份；
保留错误，下次尝试选择新的文件名。将快照复制到备份存储后，再次验证校验和。

`VACUUM INTO` 生成事务一致的快照，包括业务表和辅助表。
不要在 broker 运行期间只复制主文件，也不要对在线源数据库写入或执行外部 checkpoint。
备份连接应保持只读，并尽快关闭。
SQLite 文档中的 [WAL-reset 问题](https://www.sqlite.org/wal.html#the_wal_reset_bug)
需要多个连接并发写入／执行 checkpoint 才会触发。
本地 MQLite 数据库只有一个可写入或执行 checkpoint 的连接，另有一个使用 SQLite `mode=ro`
和 `query_only` 打开的观测读取连接；后者无法写入或执行 checkpoint。
这种职责划分加上本备份限制，避开了受影响的连接拓扑。参见[依赖策略](dependencies.md)。

### 离线目录复制

先停止生产者和消费者，再停止 broker 并确认其已经退出。
在没有进程能够修改数据时，复制完整数据目录；包含主 DB 和所有残留的 `-wal`/`-shm` 文件。
干净关停通常会执行 checkpoint 并移除这些文件，但崩溃后不能假定它们不存在。
匹配的一组文件必须一起保留。不要为了使备份看似独立而删除 WAL 文件。
目录复制结束后，才可重启原服务。

对于 systemd 方案，复制 `/var/lib/mqlite/` 前必须等待 `systemctl stop mqlite` 完成。
对于 Docker，停止容器，并使用只读挂载源卷的辅助容器复制命名卷。
在 broker 仍写入时制作卷快照，必须有该快照方式自己的、一致性保证文档。

## 恢复到全新目录

1. 保持原始数据和备份不变。验证备份校验和，并在已保存快照或工作副本上运行
   `integrity_check`、`foreign_key_check` 和文档规定的消息父项孤儿查询。
   引擎写入以事务方式约束消息关系，带索引的触发器保护父资源退役，
   因此这种关系不在 SQLite 的 `foreign_key_check` 报告范围内。
   记录 schema token 和创建该数据库的二进制版本。
2. 创建空的恢复目录或卷。在线 `VACUUM INTO` 快照是独立 DB，直接将该文件复制到空目录。
   对于离线副本，恢复完整且相互匹配的目录。绝不将快照放在来自另一次数据库生命周期的 WAL/SHM 旁边。
3. 给予 broker 账户对目录的读写权限。业务客户端保持停止，用匹配的二进制、身份验证和 `FULL`
   在隔离端点启动。不要同时挂接原数据库。
4. 将配置、订阅、消息身份和正文 hash 与记录的预期逐项核对。
   broker 启动保留租约尚未到期的 locked 行；原 token 和投递计数保持不变，直到持有者结算或到达截止时间。
   已经过期的锁会被回收：低于队列投递上限时变为 active；达到上限时带
   `MaxDeliveryCountExceeded` 进入 DLQ，旧 token 失效。
   已标记为 `deleting` 的队列不会参与锁恢复；启动先继续一轮有界清理，再由后台循环接手。
   保存的接收尝试响应仅在批次中每个 token 仍拥有保留的有效租约时才能重放。
   到期或恢复使任一 token 失效后，陈旧响应就会被移除，不能重新创造所有权。
5. 检查 deferred/scheduled/DLQ 工作和主题过滤器，再运行带身份验证的 canary。
   恢复会重放快照状态：快照之后的完成、发送、去重记录及外部业务效果，都必须与应用自己的记录对账。
   TTL 和保留时钟仍然生效。
6. 停止隔离 broker，将服务指向恢复目录，再启动其唯一所有者。
   验证后才恢复客户端。记录实际恢复时间和所恢复快照的年龄；保留原件用于调查。

可重复的[恢复演练](../test/production/restore/README.md)验证所有 schema 表和列、完整负载、
辅助记录、发件箱数据，以及显式请求的嵌入式恢复转换。
默认保留活跃租约由引擎测试和真实 Serve 重启测试另行覆盖；恢复演练不能替代这些检查。
在依赖备份之前，先对候选版本运行演练，再用具有代表性的运维数据演练同样流程。

## 升级与回滚

替换二进制前检查 schema token。仅凭版本号不能确定数据库兼容性，MQLite 也不执行 schema 迁移。

| 情况 | 流程 |
|---|---|
| schema token 相同 | 暂停客户端活动、停止旧所有者、制作一致备份、在恢复副本上启动候选并验证，再替换所有者。保留旧二进制和快照用于回滚。 |
| schema token 不同 | 将旧数据库与旧二进制配套保留。核对全部保留工作，再用候选创建新数据库。不要修改 schema token，也不要将候选指向旧文件并将其视为迁移。 |
| 候选接受业务写入之前回滚 | 停止候选，恢复匹配的旧二进制及旧快照／配置；验证后再恢复客户端。 |
| 候选接受业务写入之后回滚 | 先保留候选数据，对新消息和外部效果对账。盲目恢复旧快照会丢弃这些新写入。 |

租约恢复行为由二进制实现，不记录在 schema token 中。
安全打开默认行为引入之前的构建，即使文件本身 schema 兼容，也可能在打开数据库时收回所有活跃锁。
进行这种降级前，停止新领取，排空并结算在途工作（或等待所有租约到期），
并确认每个队列都报告 `locked=0`。
维护窗口仍有有效 token 时，不要用旧版本地 CLI 检查数据库或执行 vacuum。

从 **v0.3.0、v0.3.1、v0.3.2 或已撤回的 v0.3.3 切换到 v0.4.0** 时，
schema 从 **5 → 7**，端口 **6754** 不变。
持久化队列生命周期、固定订阅到期列及索引使数据库不兼容；没有原地迁移。
Schema 6 仅用于中间阶段尚未发布的生命周期构建，从未打标签，也会被拒绝。
遵循上面的不同 token 流程：停止生产者和消费者，制作一致的 schema-5 备份，
核对所有保留消息状态和受管理密钥，保留匹配的旧二进制／数据库组合，再用全新数据库启动 v0.4.0。
不要修改 schema token，也不要让 schema-7 代码访问旧文件。
若工作必须跨切换保留，应通过应用级排空／重放流程迁移，并保持稳定的业务身份。

v0.4.0 客户端采用删除契约
`{name,force?}`，返回有类型的 `{deleted,state}` 结果；
broker、SDK、CLI、MCP 和控制台应一起更新。
在 schema-7 接受写入后回滚，必须先保存并对账这些写入，再恢复 schema-5 快照。
对破坏性操作进行对账的整个窗口内，应在外部保存 broker stderr；
私有诊断日志独立于访问日志和数据库备份。

切换前，将 Prometheus `mqlite_queue_total` 查询替换为
`mqlite_queue_retained_messages`。
将 `mqlite_queue_oldest_message_age_ms` 替换为
`mqlite_queue_oldest_message_age_seconds`，并将阈值除以 1,000。
v0.4.0 移除了这两个已弃用别名；原生 `Observe` JSON 保留
`queues[].oldest_message_age_ms`。
恢复流量前，针对 v0.4.0 验证 recording rules、告警和仪表盘。

对于 **v0.3.1 → v0.3.2**，schema token **5**、端口 **6754**、消息数据和受管理密钥存储均不变。
遵循上述同 schema 流程；不要让 broker 重叠运行。
验证现有密钥权限和完整 canary 循环，再检查 `Observe`、监控凭据及新仪表盘／规则。
Prometheus 抓取现在默认关闭：设置 `MQLITE_METRICS=on` 或使用 `--metrics`，
才能在 API 端口保留 `/metrics`，并确保该路由不暴露于公开入口。
采集器配置独立的监控 token。
进程计数器在重启时归零；现有 Prometheus 历史数据独立于 broker 数据库。

回滚到 v0.3.1 时，先停止候选，再启动旧二进制。
现有受管理密钥保留权限，但 v0.3.1 没有 `Observe` 端点，也没有配置式监控凭据。
暂停仅适用于 v0.3.2 的观察者，并恢复原先经过授权的抓取器／规则配置；
旧 `/metrics` 端点要求管理员权限。保持管理员身份验证开启。
保留候选已接受的写入，不要盲目恢复升级前快照。
这两个已弃用指标别名在 v0.3.2 中仍可用，到 v0.4.0 被移除；参见
[指标兼容性](observability.md#compatibility-and-v040-migration)。

对于 **v0.3.0 → v0.3.1 或 v0.3.2**，schema token **5** 和端口均不变。
新版增加独立的 `access_keys` 表，不重写现有队列或消息表。
先演练打开恢复副本。回滚到 v0.3.0 会保留新增表，但旧二进制无法验证受管理密钥或执行其权限约束：
将客户端重新连接为配置式管理员 token，或保持客户端停止，直到恢复 v0.3.1 或后续版本。
存在无关且不兼容的同名 `access_keys` 表时，会在不修改该表的前提下拒绝打开数据库。

对于 **v0.2.0 → v0.3.0**，schema **2 → 5** 和默认端口 **8080 → 6754** 都改变。
切换前停止生产者，并核对**所有队列和订阅的所有状态**，包括未来定时工作、延后工作和 DLQ 消息。
使用旧版本排空保留消息，或制定明确的应用级重放方案，并保留稳定业务身份。
队列没有 active 消息，不表示其中没有 scheduled、locked、deferred 或 DLQ 工作。

在新卷／目录中创建候选数据库；同时更新端口、反向代理、客户端和探针。
保留旧二进制、配置和快照。
新二进制必须拒绝真实 schema-2 文件，旧二进制必须拒绝 schema-5 文件，且不改变其逻辑内容；
恢复演练会检查两个方向。此版本没有通用消息导出／导入迁移工具，
因此不要临时直接跨 schema 复制 SQL 表。

## 故障处置

| 现象 | 首要措施 | 恢复前验证 |
|---|---|---|
| 磁盘已满 / `SQLITE_FULL` | 停止入口流量，保留日志和已确认消息身份。扩容存储，或移除无关的过期日志／备份；绝不删除在线 DB 或 WAL。完整 `VACUUM` 需要工作空间，不适合作为紧急处置第一步。 | 后端状态、新鲜 canary、不确定请求的成功重放／对账，以及保留消息的完整性。 |
| Broker 反复崩溃 | 暂停重启循环，确保有时间保存完整 DB 目录和日志。检查磁盘、内存／OOM 与配置。只重启一个所有者。 | 孤儿锁恢复、DLQ 原因／数量、canary 和消费者幂等性。 |
| 旧积压 / DLQ 增长 | 检查消费者、租约到期／续锁和处理函数失败。检查原因及负载；先修复原因，再有界 redrive。 | 积压年龄下降，已验证的 redrive 消息身份完成结算。 |
| 队列或订阅停留在 `deleting` | 保持生产者停止并保留名称。检查存储可用性、剩余磁盘，以及 `resource_cleanup`、`subscription_expiry`、`lifecycle` 维护失败；不要用 SQL 移除生命周期行或订阅映射。清理有意采用有界方式，并会在重启后继续。 | `list` 或 `list-subscriptions --include-deleting` 不再包含该名称；此后所有者才可重建。DB/WAL 文件缩小前，逻辑空闲页已可复用。 |
| 大量订阅同时到期 | 停止继续频繁创建临时订阅。检查 active 加 deleting 清单、保留消息字节数、存储延迟、容量，以及到期／生命周期维护诊断。仍有残留行时不要重建名称。 | 到期条目在准确截止时间即不可用，deleting 清单和容量占用逐步收敛，前台延迟保持在该工作负载实测边界内。 |
| 订阅创建返回 `resource_exhausted` | 停止频繁创建，通过分页清单检查 active 加 deleting 订阅。排空或显式强制退役已放弃条目，再等待有界清理完成。调高上限也会增加元数据、扇出和观测成本。 | deleting 条目消失，容量可用，发布／观测延迟保持在该负载实测边界内。 |
| 旧数据库暴露没有订阅映射的 `kind=subscription` 队列 | 等待可用容量槽位，以预期 topic 和现有后备队列名调用 `Subscribe` 恢复映射，再保留它或通过 `DeleteSubscription` 退役。绝不要用直接 SQL 修复 MQLite 自有表。 | 准确的 topic/name 出现在 `list-subscriptions`；若已退役，则在有界清理后消失。 |
| 存储／远程超时 | 检查后端可达性和延迟。将丢失写响应视为不确定结果；重试不得超出幂等契约。 | 带身份验证的状态检查，加写入／消费 canary。 |
| `ErrSchemaVersionMismatch` | 停止本次切换尝试。恢复匹配的二进制／数据库组合。 | schema token 与正确的新旧端口；不重写 token。 |

[SQLite 备份语义](https://www.sqlite.org/lang_vacuum.html)和
[WAL 文件处理](https://www.sqlite.org/wal.html#the_wal_file)
说明这些流程背后的存储规则。
