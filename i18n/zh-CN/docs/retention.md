# 保留、删除与存储空间回收

本页跟随 `main`，目标版本为 v0.4.3。v0.3.3 已撤回且不受支持；其公开产物仅供取证或兼容性检查，
不得部署。v0.4.2 保留 v0.4.0 对 v0.3.3 的撤回声明。
v0.3.2 已有 DLQ 保留和自动本地空间回收，但除非明确注明版本差异，
下述工作预算均描述 v0.4.3 目标版本。
v0.3.2 不具备 v0.4.0 引入的队列和订阅生命周期 API。

## 哪些操作会移除保留中的消息

默认 Peek-Lock 投递提供至少一次语义。Receive-and-delete 是显式选择的至多一次 broker 移除方式，
在返回消息之前就将其删除；使用同一个接收尝试 ID 重试，可以重放已保存的响应。
持久化消息会一直保留，直到文档规定的生命周期操作将其移除或移动：

| 存储状态 | 正常生命周期 | 其他已授权的移除方式 |
|---|---|---|
| `active` | Receive 后 Complete，或 receive-and-delete | 配置为丢弃的消息 TTL；强制删除队列／订阅；订阅到期 |
| `locked` | Complete，或租约到期后返回 `active`／达到投递上限时移入 DLQ | 配置为丢弃的消息 TTL；强制删除队列／订阅；订阅到期 |
| `deferred` | ReceiveDeferred 后结算 | 配置为丢弃的消息 TTL；强制删除队列／订阅；订阅到期 |
| `scheduled` | 到预定时间时激活；Cancel 仅能取消从未投递过的定时发送 | 配置为丢弃的消息 TTL；强制删除队列／订阅；订阅到期 |
| `dead_lettered` | Redrive 或 Purge | 已配置的 DLQ 保留策略；强制删除队列／订阅；订阅到期 |

Complete 和 receive-and-delete 会立即删除该行。消息 TTL 会根据
`dead_letter_on_expire` 将到期消息移入 DLQ 或丢弃。
队列默认 TTL 同时也是 Send 显式 TTL 的上限。计时从消息首次可见时开始，
因此定时等待不会消耗 TTL；后续带延迟的 Abandon 不会重新开始 TTL 计时。
到期租约由回收器处理，消息可能重新投递，因此消费者必须具备幂等性。

去重记录、结算回执和接收尝试记录各自具有按到期时间执行的后台清理。
它们是用于运维恢复和重放的元数据，不是消息归档；此类到期删除没有逐轮行数预算。

## DLQ 保留策略

`mqlite serve` 对死信应用默认保留目标。保留工作器每 60 秒按有界批次删除符合条件的最旧死信。
这些是异步清理目标，不是准入限制：在清理轮次之间，或清理尚未追上时，队列可能暂时超过
年龄、数量或字节目标。该工作器绝不删除 active、locked、deferred 或 scheduled 状态的行。

| 设置 | Broker 默认值 | 含义 |
|---|---:|---|
| `MQLITE_DLQ_MAX_AGE` | `336h`（14 天） | 删除超过此年龄的死信，年龄从最初入队时间计算 |
| `MQLITE_DLQ_MAX_COUNT` | 每队列 `1000000` | 最多保留此数量的死信 |
| `MQLITE_DLQ_MAX_BYTES` | `0` | 可选的逐队列死信正文总字节上限；零表示禁用此限制 |
| `MQLITE_DLQ_RETENTION` | 已启用 | 设置为 `off` 可禁用所有 broker 默认值 |

嵌入式引擎默认不启用引擎级 DLQ 保留限制，除非应用传入
`WithDLQRetention(maxAge, maxCount, maxBytes)`。
逐队列的正数限制仍然会为该队列启用对应维度。

每个队列可通过 `QueueConfig`、协议中的 `config` 对象或 `mqlite create-queue` 覆盖引擎／broker 默认值：

| 逐队列设置值 | 实际行为 |
|---:|---|
| `0` | 继承引擎或 broker 默认值 |
| 正数 | 使用该队列自己的限制 |
| 负数 | 显式不限制该维度 |

字段为 `dlq_max_age_ms`、`dlq_max_count` 和 `dlq_max_bytes`。
年龄使用 `enqueued_at`，不是消息进入 DLQ 的时间。
数量和字节限制都会优先丢弃最旧的死信。

即使启用了默认值，也要监控 DLQ 数量、年龄和存储大小。
不断增长的活跃积压属于消费者容量问题，明确不在 DLQ 保留策略的处理范围内。

## 队列与订阅退役

在 `main` 上，删除队列和订阅默认要求其为空。`force=true` 是持久化的丢弃授权，
允许丢弃所有保留状态的消息，包括仍被锁定的工作，以及资源拥有的去重和重放元数据。
被锁定的投递可能已经产生外部副作用；删除消息行不能撤销该副作用。

固定订阅 TTL 会提前授予相同的丢弃权限。绝对截止时间在首次创建时保存，
更新过滤器、发布或接收消息、重试创建都不会改变它。到达截止时间后，
订阅立即退出主题扇出和数据操作路径；物理清理随后在后台进行。
显式删除仍是正常的结束方式；TTL 用于兜底清理被遗忘的资源。

接受删除的事务会将资源设为 `deleting`，并开始有界清理。
如果清理结束，同一次提交就会移除资源，调用返回 `deleted`；否则，已提交的 `deleting` 标记
会继续保留名称，由可跨重启恢复的清理过程删除其行。
前台请求最多删除 1,000 行，目标字节量约 8 MiB。每轮后续清理最多删除 4,096 个物理行，
目标字节量约 8 MiB。其普通逐资源路径每轮最多访问 32 个本地资源，
远程 Turso/libSQL 则最多访问一个资源。另有基于集合的路径可完成最多 512 个空订阅的清理，
不占用上述 32 或 1 个资源的数量额度；订阅映射行和后备队列行仍计入共享行数预算。
单行过大时允许超过字节目标，以保证清理仍能推进。

默认订阅容量为 10,000，包含 active 和 deleting 映射。
在物理清理结束前，映射会一直占用容量槽位。因此，大规模强制删除或同时到期的资源波峰
可能形成清理积压、增大 WAL、延迟名称复用，并暂时拒绝创建新订阅。

常规请求／响应流量应保留稳定的回复订阅，并通过 `correlation_id` 分发。
确实需要临时订阅时，使用全局唯一且仅使用一次的名称，完成后显式删除，
再加固定 TTL 兜底，并错开到期时间。条件允许时先排空再删除。
仅在有意放弃保留工作时使用强制删除。

必须由一个控制方串行处理删除与同名重建。收到不确定的响应后，使用只读的分页清单，
并包含 deleting 条目。等待名称彻底消失后再重建；替代资源已经存在时，不要重放旧删除请求。

## 本地文件空间回收

删除行后，SQLite 页面立即可以复用；这不保证数据库文件或 WAL 文件会立刻缩小。
新建的本地数据库使用 `auto_vacuum=INCREMENTAL`。

在 `main` 上，后台空间回收器每 60 秒运行一次。当空闲页面至少为 256 页时，
它会执行 checkpoint，并每轮最多向操作系统归还 256 页。因此，一次性的大规模删除可能
需要多轮才能完成回收。v0.3.2 的间隔和阈值相同，但会尝试在一轮内排空当前 freelist；
它没有 `main` 的 256 页工作量上限。读取方持有快照时，WAL 也可能增长，
待读取方结束并完成 checkpoint 后再缩小。

运维命令可以显式回收空间：

- `mqlite vacuum` 执行 checkpoint，并排空当前 incremental-vacuum freelist。
  大规模清除后，通常手动选择该命令。
- `mqlite vacuum --full` 重写数据库，并占用全局写入器。
  仅在经过安排的维护窗口中使用。

远程 Turso/libSQL 自行管理其物理存储。
客户端不暴露远程数据库或 WAL 文件大小，本地 vacuum 命令也不适用于远程存储。

本地存储容量应覆盖最大同时积压、WAL 增长、备份空间，以及有界清理和空间回收所需的时间。
应监控剩余磁盘空间、保留中／删除中的资源清单、维护失败及最旧消息年龄，
不要假定删除后文件大小会立即下降。

## 删除前导出死信

MQLite 没有内置归档接收端。运维人员可以组合现有操作：

1. 暂停所选 DLQ 范围内的变更，或以其他方式进行协调。
2. 使用 `Peek(state=dead_lettered)` 读取死信，将 `from` 推进至最后导出序号之后，
   并将消息持久化写入外部存储。
3. 验证外部副本。
4. 暂停变更后，只有在导出已覆盖目标 DLQ 范围时才执行清除。
   视情况使用 `max` 或 `older_than` 限制。另一种方式是 Redrive 到专用队列，
   由其消费者先将每条消息写入归档，再完成消息。

Peek 不会破坏原消息，也不会让导出与清除成为同一事务。
Redrive 会原子地移动每个选中的内部批次：源端删除与目标端插入一起提交。
专用队列到外部归档的投递仍为至少一次，因此归档消费者必须具备幂等性；
Redrive 不会让外部归档交接变成同一事务。
