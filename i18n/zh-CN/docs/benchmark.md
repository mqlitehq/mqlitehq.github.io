# mqlite 基准测试、容量规划与调优

本文展示 mqlite 引擎在真实工作负载下测得的、可复现的数据——**并非**单一吞吐量数字——并说明这些数据对**部署容量规划**与**调优**的意义。测试套件覆盖吞吐量、写放大、**整个进程的内存与回收**、**数据库文件膨胀与回收**、**携带键值属性的丰富消息**、**消息体大小扫描**，以及**负载升降与消费者反复上线下线**。测试分别在**本地**（高速多核机器）和有意选择的微型**云端**机器上运行，呈现不同条件下的真实表现。

> 原则：先测量，再作结论。以下每组结果都注明测试程序与运行环境；仓库中提交的测试程序包括 `test/bench/` 和原生 Go 基准测试。这些是历史工作负载测量结果，不构成任何版本的容量保证。在选择内存或 CPU 限额前，请用自己的消息大小、并发度、队列数量和监控负载重新测试当前二进制程序。

## 容量规划与部署（Fly.io）

下面的历史样本在一台 256 MB 的 Fly 机器上运行单个 broker。这些测量值只能作为针对具体工作负载开展容量测试的起点；它们并未确定安全的积压阈值，也不代表当前版本的镜像大小。

```
┌─────────────┬──────────────────────────┬──────────────────────────────────────┐
│ resource    │ measured (1 broker)      │ Fly choice                            │
├─────────────┼──────────────────────────┼──────────────────────────────────────┤
│ memory      │ 19 MB idle               │ 256 MB used in the historical test   │
│             │ 38 MB @ 50k msgs queued  │ validate current peak memory first   │
│             │                          │ no universal backlog threshold        │
│ disk        │ ~0.4 KB / 256 B message  │ 1 GB volume  (~1.1M planned msgs)     │
│             │ + ~4 MB WAL in this run  │   size = backlog × 0.6 KB × 1.5       │
│ vCPU        │ tiny/op; 1000s/s batched │ 1 shared vCPU in the measured setup   │
│ image       │ 10.9 MiB static binary   │ distroless/scratch ≈ 15 MB image,     │
│             │   (CGO-free)             │   cold start < 1 s (scale-to-zero ok) │
└─────────────┴──────────────────────────┴──────────────────────────────────────┘
```

**拓扑：**mqlite 采用**单写入者**模型：每个数据库运行一个 broker 或一个嵌入式 `Engine`。本地进程持有文件锁，因此每个卷只运行一台机器，不要让多台机器通过水平扩容共同使用同一个 SQLite 文件。Turso/libSQL 提供托管远程存储，但这不意味着多个 broker 可以安全地重叠运行；参见 [turso.md](turso.md)。

积压消息的峰值深度是磁盘容量规划的主要输入，而不是整个生命周期的吞吐总量（`Complete`/`Purge` 会删除行）。还要为 WAL 增长、SQLite 页面和索引开销、回收滞后、延迟检查点的读操作以及备份留出空间。后台 `incremental_vacuum` 会随时间将空闲页面归还给操作系统（见 §3），但这并不能让积压估算成为文件大小的硬上限：

| 积压深度（256 B 消息） | 磁盘上的数据库 | Fly 卷 |
|--------------:|-----------:|:-----------|
| 100k          | ~40 MB     | 1 GB       |
| 1M            | ~0.4 GB    | 1 GB       |
| 5M            | ~2 GB      | 3 GB       |

## 环境

| | 本地（基线） | 云端（受限） |
|---|---|---|
| 位置 | 开发机器上的 Docker（`run-bench.sh`） | Fly.io 应用 `mqlite-bench`，区域 `sin` |
| CPU | 12 vCPU，arm64（Apple Silicon，linuxkit 虚拟机） | **shared-cpu-1x → `GOMAXPROCS=1`**（一个 amd64 核心的*部分*算力，存在 CPU-steal） |
| 内存 | 8 GB | **256 MB**（≈207 MB 可用） |
| 磁盘 | Docker 虚拟机内的 overlayfs | 机器根文件系统 **overlayfs**（基准测试没有挂载卷） |
| 探针 | `/proc/self/{io,stat}` + 每 200 ms 采样一次 RSS/堆/文件 | 相同二进制程序，相同测试矩阵 |

对环境限制的说明：本地主机为 arm64，运行在 Docker Desktop 的 linuxkit 虚拟机中，因此 12 个核心会让并行场景的数据显得更好，磁盘也经过虚拟化。Fly 机器反映的是最廉价部署中**仅有部分单核算力的现实条件**。两边都通过 `/proc/self/io` 测量磁盘写入字节数；这里关注的并非绝对磁盘延迟，而是**相对**写放大以及内存和文件的表现，这些特征在两个平台上一致。

## 如何复现

```bash
# local — builds the bench image, runs the matrix on the container's own fs
BENCH_DUR=3s ./test/bench/run-bench.sh          # → test/bench/out/results.json

# opt-in queue create/send/force-delete/converge churn
BENCH_ONLY=lifecycle_churn BENCH_DUR=2s ./test/bench/run-bench.sh

# hermetic HTTP-Hrana logical-lease trend (loopback; no Turso credentials)
go test ./engine -run '^$' -bench '^BenchmarkHranaSingleLeaseExec$' -benchmem -benchtime=3s
```

历史 Fly 测试使用了特定环境的部署文件，该文件不在本仓库内。复现云端测量时，请部署仓库中提交的 `test/bench/Dockerfile`，明确指定自己的机器、区域、卷和清理配置，并将这些输入与结果一并记录。

按时间驱动的场景运行 `dur` 指定的时长（历史矩阵中为 3 秒）；固定数量的排空和膨胀场景则运行到其有上限的预填充消息全部完成核对。之后，每个场景都会进入**空闲 + GC + FreeOSMemory** 阶段，以测量实际*回收*了多少资源。后台采样器每 200 ms 记录一次 RSS、Go 堆以及数据库/WAL 文件大小；每个场景结束时会输出一行 `[done]` 或 `[fail]`（因此，即使受限机器提前停止，已经尝试的场景仍有诊断信息）。

测试运行器遇到工作负载操作错误时按失败处理：固定数量的排空必须与预填充数量精确相符，混合工作负载必须核对已接受消息数等于已完成与剩余消息数之和，结果文件写入失败也会使进程非零退出。对远程 `-db` 测试，请使用专用的非生产数据库。每个进程使用唯一的队列命名空间，每个场景结束后只强制删除该命名空间，并执行有界清理；被中断的进程仍可能留下其私有命名空间。

可选的 `lifecycle_churn` 场景使用一组固定的 64 个队列名，在删除收敛之前绝不复用名称。每轮先创建队列、发送小批消息、接受强制删除，再运行有界维护，直到所有名称均不存在。其中四个队列各含 1,024 条消息，以覆盖清理尚未完成的情况；另外 60 个队列各含 16 条消息。存活消息体的总载荷保持在 1 MiB 以下。结果报告即时与待完成回执、维护轮次、收敛延迟、载荷峰值以及数据库/WAL 大小。这里的 `ops/s` 指每秒完全收敛的队列生命周期数量；通用延迟列测量的是最初的删除回执。

在 Apple M1 Pro 上最终执行的一次 2 秒原生强制删除冒烟测试中，共完成 640 个队列生命周期（10 轮），速率为 289.17 个生命周期/秒。全部 640 次删除均被接受，其中 40 次需要类似后台任务的清理；收敛延迟 p99/最大值为 67.519/85.309 ms；数据库峰值为 5.528 MiB，最终为 0.480 MiB，WAL 为零字节。这次短测试用于发现回归，不是部署容量声明；请在目标 CPU、文件系统、耐久性模式、消息大小以及适用的远程后端上复现。

原生 Go 基准测试覆盖主题扇出、订阅创建/空订阅删除的反复操作，以及包含精确总数的订阅分页：

```bash
go test ./engine -run '^$' \
  -bench 'Benchmark(TopicFanout|SubscriptionCreateDelete|ListSubscriptionsPage)' \
  -benchmem -count=5
```

在使用 Go 1.26.9 的 Apple M1 Pro 上，最终记录的创建/删除生命周期中位数为：保留 100 个订阅时 323.955 µs，保留 10,000 个订阅时 328.866 µs（1.015×）。查询含精确总数的 100 项页面，在 1,000 个订阅时测得 0.652 ms，在 10,000 个订阅时测得 5.168 ms。一次含 5,000 条排队消息的冒烟测试在 3.203 ms 内确认强制删除，并在一轮耗时 29.367 ms 的维护中完成收敛。这些控制平面测量未发现明显的生命周期性能回归，但精确计数的开销会随清单规模增长；不要把 10,000 个订阅的安全上限当成低延迟保证。

原生套件还覆盖固定生命周期的扇出，以及使用索引的订阅到期扫描：

```bash
go test ./engine -run '^$' \
  -bench 'Benchmark(TopicFanoutTTL32|SubscriptionExpiry)' \
  -benchmem -count=5
```

在同一台使用 Go 1.26.9 的 Apple M1 Pro 上，执行了七轮交替的一秒测试，将固定生命周期实现与引入 TTL 支持前的相同套件作对比。延迟中位数变化分别为：`SendOne` +2.50%，`SendBatch64` -0.43%，32 路主题扇出 -3.32%，256 路扇出 -0.45%，接收后完成 +0.86%。这些变化均低于 10% 的调查阈值。另一次使用相同二进制程序的对比中，32 路固定生命周期扇出的中位数为 1.512 ms；按各组独立中位数计算，比永久订阅高 3.62%；每次发布增加 32 次分配和 255 字节。共享主机的波动意味着，无论这些小幅改善还是小幅成本，都不能作为优化效果或 SLA 声明。

对 10,000 个未来截止时间进行索引到期扫描，一轮无工作扫描耗时 56.808 µs（17,603 轮/秒）。将整批 1,000 个已到期订阅转换状态耗时 3.306 ms（302,459 个订阅/秒）。一次受控突发测试创建了 10,000 个订阅，其中一个积压 5,000 条消息，然后将它们推进到同一截止时间。数据平面立即受到隔离限制；通过手动驱动的 19 轮有界维护，在 338 ms 内丢弃积压并移除全部元数据。正常后台工作任务下，10,000 个空订阅在 1.292 s 内完成收敛。清理期间，一个永久队列未出现发送错误；发送 p50 保持在约 0.1 ms，而 p99 从到期前的 0.687 ms 上升到突发期间的 12.003 ms（最大 34.499 ms）。这是大量同时到期带来的预期、有界尾延迟成本，不是容量承诺；应错开截止时间，并对目标后端开展负载测试。

为每页 100 项的订阅页面添加必需的生命周期时间戳后，清单规模为 1,000 项时，中位数从 0.658 ms 变为 0.712 ms（+8.21%）；10,000 项时，从 5.187 ms 变为 5.325 ms（+2.66%）。采用精确预分配后，页面内存从约 39 KB 降至 30 KB；分配次数基本不变。

## 深度当前积压下的观测成本

原生观测基准测试使用 300 个队列，同时保留 300,000 条消息。这是当前积压，不是 broker 的累计吞吐量：已完成的消息通常会在结算时离开消息表。运行仓库中提交的测试数据集：

```bash
go test ./engine -run '^$' \
  -bench 'Benchmark(ObservationDeepBacklog|SendDuringDeepObservation)$' \
  -benchmem -count=3
```

每队列的 `Stats` 使用针对各状态的索引。全局 `Observe` 的共享缓存约每 10 秒需要刷新，届时仍必须扫描保留行；缓存命中也仍要分配并序列化完整队列响应。刻意设置为不利条件的 `continuous_observe` 基准会以尽可能快的频率调用观测；它属于压力场景，不是建议的抓取间隔。

最终的聚合查询将逐状态的 `SUM` 表达式替换为选择性 `COUNT ... FILTER` 聚合，同时保留单次分组扫描。在使用 Go 1.26.9 的 Apple M1 Pro 上，三次测试各测量三次刷新，结果如下：

| 当前保留消息的分布 | 原 `SUM` 中位数 | 当前 `FILTER` 中位数 | 中位数变化 |
|---|---:|---:|---:|
| 300,000 条 active 消息 | 248.369 ms | 210.754 ms | -15.14% |
| 六种状态各 50,000 条 | 244.973 ms | 210.518 ms | -14.06% |

该测试隔离了聚合表达式的成本，不是部署容量测试结果。即使本地文件使用独立的只读观测连接，刷新成本仍与保留行数成正比，并会争用 CPU、页面缓存、存储带宽以及 WAL 检查点的余量。

一次五组配对的本地文件压力测试，以每秒 1,000 次发送的计划投放速率，对比各为 20 秒的基线阶段和启用监控阶段。每个监控阶段均执行了预期的全局刷新与每队列调用；每条获准进入的消息都完成了处理，每个阶段均以零积压结束。预先选定的“配对中位数变化达到 10% 则调查”阈值，在所有前台 p99 指标上均未通过：

| 指标 | 启用监控后的配对中位数变化 |
|---|---:|
| 吞吐量 | -1.06% |
| 丢弃的计划投放时隙 | +1.05 个百分点 |
| Send p99 | +18.50% |
| Receive p99 | +14.80% |
| Complete p99 | +53.03% |
| 端到端 p99 | +154.12% |

主机波动影响明显，各配对的变化方向也并不相同，因此，该测试支持的结论是：在该投放负载下吞吐量稳定，已完成工作量可核对。它**不能**证明监控不会增加前台尾延迟。另一次每秒发送 500 条消息的测试也包含一个严重不利窗口，因此没有确定一个尾延迟安全的运行点。

在每秒 1,000 条的测试中，监控阶段的 WAL 峰值为对应基线的 4.32–5.34 倍。每个阶段结束后，被动检查点报告没有占用中的读操作，且全部帧均已完成检查点处理；之后执行的截断检查点使 WAL 归零。因此，即使读操作结束后可以回收文件，观测也可能导致暂时的 WAL 增长。生产环境应从 15 秒的抓取间隔开始，再结合目标积压与硬件，测量刷新耗时、WAL 增长和前台 p99。

## 远程 Turso 趋势浸泡测试

手动触发的 **Turso 性能浸泡测试** Action 让一个包内部 Engine 直接访问专用验证数据库。它独立于 HTTP broker，使用四条闭环测试通道：两个标准队列、一个 `group_fifo` 队列和一个 `strict_fifo` 队列。每条通道反复发送一个唯一的 256 字节消息体，接收并验证该消息体完全一致，然后完成消息，再开始下一轮。这样既能保持存活消息工作集有界，又能运行正常的后台维护。

四条逻辑通道共享一个固定准入限制：测试程序最多同时进行一次数据库调用（`metadata.json` 中的 `foreground_max_in_flight=1`）。它们的初始启动时间名义上分别错开 0、250、500 和 750 ms；元数据将其记录为 250 ms 的通道启动错峰。相对于四连接的远程连接池，这样可以避免同步启动突发，并将前台调用需求保持在连接池上限以下，为正常后台维护留出余量。该配置有意采用可持续的稳定性与趋势负载。它不是容量测试，其吞吐量不能解释为后端的最大吞吐量。

准入限制只适用于测试程序发起的调用。Engine 后台工作任务绕过该限制，而且它并不预留 Turso 主节点上串行化的写锁。

触发工作流时可选择 2、10 或 30 分钟。先运行 2 分钟，验证凭据、清理和证据收集；再用 30 分钟完成预期的持续趋势检查。该工作流与已有 Turso nightly 套件共享一个仓库级并发锁，因为两者都会通过 `TestMain` 重置同一数据库。两个工作流在测试获准重置数据库前，都会按失败关闭原则校验验证主机白名单。绝不能将任一工作流指向生产数据库。

产物每分钟记录一次数据，最后不足一分钟的窗口也会额外记录一次，内容包括：各通道及总体的 cycles/s；Send、Receive、Complete 和端到端的 p50/p95/p99 与最大延迟；空结果/错误计数；队列积压；结算回执计数；存储结果与重试；连接池等待；后台维护轮次状态；以及运行器能够提供的 Go 堆、RSS、goroutine、GC 和进程 CPU。维护快照从进程内存复制，不会额外查询远程数据库。`metadata.json`、`windows.jsonl`、`summary.json`、`summary.md` 和测试日志保留 14 天。错误、消息体不匹配、账目核对失败、最终仍有积压或精确清理失败，均使测试失败；失败前已经写出的证据仍可上传。前台失败和各窗口的存储错误记录安全生成的类别、可获得的 HTTP/SQLite 状态，以及单向错误指纹。证据中绝不复制提供方文本、URL、凭据或消息体；指纹仅用作关联私有日志的键。

单次非最终 `Stats` 或结算回执计数采样，如果以 `connection` 类别失败，会被记录为缺口，并允许在下一个计划采样时恢复；测试程序不会发起额外查询来强行恢复。在该缺口期间，总体及各通道的积压和结算回执字段均为 `null`，旧值不会作为最终状态展示。整次测试中任意位置的第二次监控失败、任何其他操作或错误类别（包括工作集不变量），或者最终采样失败，都会使浸泡测试失败。每个窗口记录结构化的监控状态，摘要记录失败采样次数与恢复状态。

单次失败的维护轮次可以在该任务下一次完整轮次中恢复。连续两轮失败，或测试结束时仍有一次失败未恢复，都会使浸泡测试失败。已恢复的失败仍会显示在累计维护计数器和有界诊断历史中。最终维护判定来自进程内存快照，该快照在 `Engine.Close` 停止并等待后台工作任务退出后获取；测试程序不会额外触发一轮维护来改变结果。因此，`windows.jsonl` 的最后一项是清理前的工作负载采样，而 `summary.json.final_maintenance` 是关闭后的终态。运行器取消或外层测试超时可能中断最终清理；下一次测试的 `TestMain` 重置和按命名空间进行的启动清理会移除这些残留。

首个到最后一个窗口的变化仅作描述，没有性能阈值，因为 GitHub 托管运行器的位置、共享 CPU 和网络路径都会引入噪声。Turso 不通过该客户端提供物理数据库或 WAL 文件大小；对应 JSON 字段为 `null`，绝不使用容易误导的零值。结算回执保留 30 分钟，因此一次 30 分钟测试的最终回执数是当前保留窗口的快照，不是整个生命周期内的完成总数。

## 1 · 吞吐量与写放大

除另有说明外，消息体均为 256 B。`wB/op` = 每次操作物理写入磁盘的字节数（写放大）。**本地机器有 12 个高速核心；云端机器只有受限单核的部分算力**——应将两列理解为“引擎特性”与“最廉价真实机器”的对比。

| 场景 | 同步模式 | 本地 ops/s | 云端 ops/s | 本地 wB/op | 云端 wB/op |
|---|---|---:|---:|---:|---:|
| produce_p1 | NORMAL | 15,926 | **4,000** | 9,740 | 9,696 |
| produce_p4 | NORMAL | 17,449 | **567** | 9,744 | 9,667 |
| produce_p8 | NORMAL | 17,963 | **322** | 9,745 | 9,635 |
| batch_16_p4 | NORMAL | 30,748 | 1,600 | 1,979 | 1,928 |
| batch_64_p4 | NORMAL | 35,146 | **6,000** | 1,090 | 1,045 |
| e2e_4x4 | NORMAL | 4,413 | 197 | 58,539 | 55,809 |
| sessions_64g | NORMAL | 3,789 | 164 | 71,016 | 67,794 |
| produce_p4_FULL | **FULL** | 1,556 | 468 | 13,743 | 13,682 |
| props_p4 | NORMAL | 15,909 | 1,000 | 10,577 | 10,493 |
| props_batch64 | NORMAL | 24,161 | **6,700** | 1,641 | 1,622 |

**这两次测试的写放大相近**——每项云端 `wB/op` 与对应本地值的差异均在 5% 以内。样本表明，这项成本主要由 SQLite + WAL 决定（单条发送一条 256 B 消息约写入 9.7 KB，批量发送约为 1.1 KB），但两个环境不足以确立一个与平台无关的常数。容量规划前，请测量目标文件系统与工作负载。

**在仅有部分单核算力时，并发会*降低*性能**——`produce_p1` 4.0k > `produce_p4` 567 > `produce_p8` 322。`GOMAXPROCS=1` 没有可利用的并行算力，增加生产者只会在唯一写入者上增加锁争用，以及调度器/GC 的频繁切换。廉价机器上合适的模式是**由一个生产者批量发送**，而非多个生产者并发逐条发送。

**批量发送显著缩小了差距**——在*同一个*受限核心上，单条 `produce_p4` 只有 567/s，而 `batch_64` 达到 6.0k/s（≈10×），写放大约为原来的 1/9。带丰富属性的批量发送（`props_batch64`）保持 6.7k/s。

**FULL 耐久性**在本地的成本约为 11×；已经受 CPU 限制的云端机器上，差距缩小（468 对 567），因为那里的瓶颈是 CPU 核心，而非 fsync。

## 2 · 短暂空闲后的内存占用

这里测量整个进程的 **RSS**（不仅是 Go 堆），对比负载期间的峰值与测试程序短暂空闲 1.9 秒并强制 GC 后的值。这份结束快照描述即时进程状态，并不意味着每 60 秒运行的存储清理任务已经执行。

| 场景 | 本地峰值 → 短暂空闲 | 云端峰值 → 短暂空闲 |
|---|---:|---:|
| produce_p8 | 34 → 27 MB | 27 → 20 MB |
| batch_64_p4 | 32 → 27 MB | 28 → 23 MB |
| props_batch64 | 33 → 29 MB | 29 → 25 MB |
| size_16KB | 33 → 29 MB | 27 → 23 MB |
| drain_4c（200k 条消息） | 33 → 28 MB | —（见 §7） |

**上表各场景的峰值 RSS 为 27–34 MB。** 本地 200k 条消息排空场景与 16 KB 消息体场景均处于这个实测范围内。SQLite 将积压存储在磁盘上，但这不能界定 broker 的全部内存。停止负载后 RSS 下降；这些测试中没有观察到持续增长。更大的消息、更多并发请求或队列，以及监控，都可能改变内存占用。选择内存限额前，应测量当前工作负载。

## 3 · 数据库文件占用与回收

`bloat_50k` 现在只插入一次、且恰好插入 50,000 条消息，对全部积压采样，再通过 `Complete` 精确排空同样数量的消息，并将任何发送、接收、结算或数量核对错误判为失败。`file_bytes_per_msg` 使用预填充时实际接受的数量。该场景的旧结果不可比：之前的测试程序预填充两次，将每个尾批次向上取整，却仍用文件大小除以 50,000。

该场景的 `db_final_mb` 是与其他场景相同的 1.9 秒空闲后的即时状态。它适合对比峰值与排空后的文件，但无法验证后台页面回收。本地文件数据库使用 `auto_vacuum=INCREMENTAL`；后台清理任务每 60 秒检查一次，在达到 freelist 阈值后回收有上限的页面数量。评估回收时，请运行覆盖这一间隔的测试，或者测量显式 `Compact(false)`。远程 Turso 自行管理存储。

## 4 · 丰富消息——键值属性

`props_*` 发送符合实际使用的消息：包含 `Properties` 映射（tenant / trace_id / event_type / priority / source / schema_ver）以及 CorrelationID、Subject、ContentType——将这种“正常用法”与仅有消息体的情况作对比。

| 场景 | 本地 ops/s | fileB/msg | 相较纯消息体 |
|---|---:|---:|---|
| produce_p4（纯消息体） | 17,449 | 415 | — |
| props_p4 | 15,909 | 693 | 磁盘每条消息 +280 B，约慢 9 % |
| batch_64_p4（纯消息体） | 35,146 | 373 | — |
| props_batch64 | 24,161 | 664 | 每条消息 +291 B，批量发送约慢 31 % |

单条发送时属性成本较低（吞吐量约减少 9 %，每条消息 +280 B），但批量发送时成本更高（约 31 %）：提交开销被分摊后，逐条对键值映射进行 JSON 编码就成为主要工作。

## 5 · 消息体大小扫描

4 个生产者，NORMAL，消息体 64 B → 16 KB：

| 消息体 | 本地 ops/s | 云端 ops/s | wB/op（两边约相同） | fileB/msg |
|---|---:|---:|---:|---:|
| 64 B | 17,205 | 1,200 | 9,122 | 217 |
| 256 B | 17,449 | 567 | 9,744 | 415 |
| 1 KB | 13,991 | 912 | 12,980 | 1,489 |
| 4 KB | 12,547 | 454 | 22,205 | 4,740 |
| 16 KB | 7,988 | 259 | 46,939 | 17,091 |

这次扫描中，磁盘存储量与消息体大小大致成线性关系。消息体大小与 `fileB/msg` 的实测差值为 153 到 707 字节，因此该表不足以支持一个固定的行/索引开销常数。消息体约不超过 256 B 时，吞吐量主要受提交限制；之后逐渐受字节处理量限制。默认消息体上限为 1 MiB（`MaxMessageBytes`）。

## 6 · 负载升降与消费者反复上线下线（本地）

- **rampdown_4x4**：高强度生产，然后停止生产，由消费者排空至空闲。负载消失后，RSS 从峰值 31 MB → 27 MB——内存会随工作负载*下降*，而非只增不减。
- **churn_consumers**：生产者保持稳定，消费者分组反复**上线/下线**。多个周期内 RSS 保持约 28–34 MB，**没有阶梯式增长**——连接/断开没有造成泄漏。

## 7 · 云端现实——256 MB 与部分单核算力带来的变化

Fly `shared-cpu-1x` 使用 `GOMAXPROCS=1`，且存在 CPU-steal。与本地 12 核机器相比：

1. **实测场景中的内存保持较低水平。** §2 云端场景的峰值 RSS 为 27–29 MB，负载结束后有所回收。这并未确定其他工作负载或当前版本所需的内存。
2. **两次测试的写放大接近。** 云端值与本地值的差异在 5% 以内；应在目标存储栈上验证这种关系。
3. **吞吐量受核心算力限制，并发适得其反。** 多生产者单条发送吞吐量大幅下降（p4 为 567/s，p8 为 322/s），因为没有第二个核心。**批量发送后，吞吐量恢复到每秒数千条**（6.0–6.7k）。
4. **尾延迟体现限速影响。** 大多数多 goroutine 场景的 p99 达到直方图的 100 ms 上限（CPU-steal 导致停顿）；单生产者场景的 p99 保持在约 5 ms 以下。

在这组简短的历史样本中，shared-cpu-1x 上批量发送约达到 6k msg/s，而并发单条发送只有每秒数百条。这些是工作负载观察结果，不是持续容量或 SLA 声明。

## 调优参数

mqlite 提供合理的默认值；大多数部署无需改动。以下按大致影响程度排列：

| 参数 | 默认值 | 何时调整 |
|---|---|---|
| **批量大小**（`messages:[…]`） | — | 最有效的手段——写放大约降至原来的九分之一（9×），吞吐量约提高 2×。尽可能使用批量。 |
| **`MQLITE_SYNC`** | `NORMAL` | 只有在无法接受断电丢失最近几次提交时才使用 `FULL`；单条发送的成本约为 11–18×，因此应搭配批量发送。 |
| `wal_autocheckpoint` | 1000 页（~4 MB） | 适用于没有长时间读操作的历史基线；观测快照和其他读操作可能导致更大的暂时性 WAL。只有测量检查点与恢复之间的权衡后才提高。 |
| `cache_size` | ~2 MB | 工作集（队列头部 + 索引）很小；只有性能分析表明深度积压下存在缓存压力时才提高——256 MB 机器上的 RAM 成本不可忽略。 |
| `mmap_size` | 关闭 | `modernc.org/sqlite` 是纯 Go 实现；不要假定它会得到 C-SQLite 的 mmap 收益——先测量。 |
| 写入者/提供方连接池 | 本地写入者 1 / 远程提供方 4 | **不要修改**——本地写入连接池保持一个连接，以保证原子 claim；本地文件另有一个只读观测连接。远程连接池仅属于单个 broker，Turso 会串行化提交。`libsql://` 逻辑连接采用单次连接租借，而共享 HTTP 传输层保持 TCP/TLS 复用；参见 [turso.md](turso.md)。 |

本地 modernc SQLite 连接设置了 `busy_timeout=5000` 和 `temp_store=MEMORY`。这些设置不适用于远程 Turso/libSQL 连接；其瞬时争用使用 [turso.md](turso.md) 所述的有界重试策略。

## 结论汇总

1. **实测内存较低，且能够回收**——§2 场景中的峰值 RSS 为 27–34 MB。记录的消费者反复上线下线和负载下降测试中没有观察到持续增长；应单独验证当前工作负载。
2. **批量提升速度**——写放大约降至原来的九分之一（9×）；在单核上，这意味着*每秒数百条*与*每秒数千条*的差别。
3. **两个历史环境中的写放大相近**（单条约 9.7 KB/op，批量约 1.1 KB，本地/云端配对差异在 5% 以内）；这不是适用于所有平台的常数。
4. **单写入者模型**：更多生产者 ≠ 更高写吞吐量；在单核上反而*更差*。优先使用一个批量发送的生产者。
5. **峰值积压是容量规划的主要输入。** 为 WAL、页面/索引开销、碎片、回收滞后、长时间读操作和备份留出余量；后台 `incremental_vacuum` 会随时间归还符合条件的空闲页面。
6. **NORMAL 与 FULL** 是成本约差 11× 的耐久性选项（本地）；应根据主机故障模型选择。
7. **属性成本可接受**；大消息体受字节处理量限制，存储量呈线性增长。

历史源产物记录在 `test/bench/out/results.json` 和 `mqlite-bench` Fly 日志中；这些产物不随本仓库提供。应将表格视为历史证据，在将这些数字用于当前部署决策前，重新运行上述命令。
