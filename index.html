# what it solves

Three problems that keep re-appearing in every backend.

“I need background jobs, not a broker deployment.”

A cluster to operate, an SDK to learn, a bill to pay — for one service.
→ a library over one file

Zero infrastructure. Want HTTP later? The same engine runs as one ~30 MB process.

“My DB write and my event can disagree.”

Save the order, publish the event — crash in between and they split. Outbox tables and CDC are yet more machinery.
→ one transaction for both

The queue is your SQLite DB: business write + enqueue commit atomically.

“My hand-rolled jobs table became a bad broker.”

A status column and a polling loop slowly regrow locks, retries, dead-letters — untested.
→ these semantics come finished

Peek-Lock, retries → DLQ + redrive, FIFO groups, delays, dedup — pinned by a conformance suite.

# why mqlite

Design priorities, in order — when they conflict, the earlier one wins.

1Lightweight & embeddable

One pure-Go binary over one SQLite file. No broker cluster, no sidecar, no CGO. Start embedded; move the same code to a broker, or the storage to replicated Turso, without rewriting your app.

2Reliable under concurrency

Default Peek-Lock delivery is honestly at-least-once; explicit receive-and-delete chooses at-most-once broker removal. New settlements require a current token and unexpired lease; idempotent send/receive/settle, single-broker crash recovery, and O(log n) claims on a deep backlog. FIFO groups stay ordered even across consumer crashes and lock expiry.

3Simple, unambiguous interface

Every operation is one HTTP POST with a JSON body — 29 routes in source v0.4.2, curl-able by construction, exactly one settlement verb per outcome (Complete / Abandon / Reject / Defer), no aliases. Easy for people; easy for agents.

4Service Bus flavor, not a clone

Peek-Lock, group_id sessions, DLQ + redrive, scheduling and duplicate detection feel familiar from Azure Service Bus — in an idiomatic-Go shape, with the whole model documented and its public compatibility invariants pinned by a conformance suite.

# the killer feature: a transactional outbox with no outbox

Because the queue is your SQLite database, a business write and its event commit in one transaction. The message exists if and only if the order does — no dual-write race, no CDC pipeline, no poller.

Embedded-only: this shape avoids a separate broker or Postgres dependency. External brokers can't join your SQLite transaction, and Postgres-based queues need a Postgres. Here the business data and queue share one file.
package main

import (
    "context"
    "log"

    "github.com/mqlitehq/mqlite"
    "github.com/mqlitehq/mqlite/engine"
)

func main() {
    ctx := context.Background()
    mq, _ := mqlite.OpenEmbedded(ctx, "file:./app.db")
    defer mq.Close()
    _ = mq.CreateQueue(ctx, "order-events", mqlite.QueueConfig{})

    err := mq.Tx(ctx, func(tx *engine.EngineTx) error {
        // 1) the business write, on the SAME transaction. Use tx.Context(), not the
        //    ctx you passed to Tx — a statement interrupted mid-transaction wedges
        //    a local SQLite database.
        if _, err := tx.SQL().ExecContext(tx.Context(),
            `INSERT INTO orders(id, total) VALUES(?, ?)`,
            42, 1999); err != nil {
            return err // rollback: nothing enqueued
        }
        // 2) enqueue — commits atomically with it:
        _, err := tx.SendOne("order-events",
            engine.OutMessage{Body: []byte(`{"order":42}`)})
        return err
    })
    if err != nil {
        log.Fatal(err)
    }
    // Either both happened, or neither did.
}

# how it works

Two delivery targets, one storage story: a topic stores nothing — the thing that stores, is consumed, and can dead-letter is always a queue.

The publisher sends order.created to the implicit events topic.

  1. 01 · publishThe publisher sends order.created to the implicit events topic.
  2. 02 · routeThe topic stores nothing. Both subscription filters match this message.
  3. 03 · copyaudit and fulfillment each receive an independent backing-queue copy: same message ID, different sequence numbers.
  4. 04 · claimEach Receive changes its copy from active to locked and increments delivery_count to 1.
  5. 05 · settle differentlyaudit completes, so only its message copy is removed; the subscription remains. Below the delivery limit, fulfillment abandons with delay, moving its copy locked → scheduled without incrementing the count.
  6. 06 · dueThe scheduler returns the delayed copy to active. Its delivery count is still 1.
  7. 07 · retryThe next Receive locks the copy and increments delivery_count to 2.
  8. 08 · completeThe retry completes, so that message copy is removed too; both subscriptions remain. Delivery is at-least-once, so handlers must remain idempotent.

Animation timing is illustrative, not broker latency. A final ordinary claim may still renew and complete at the delivery limit. It enters the DLQ if explicitly rejected, or if that final lock is abandoned, expires, or is recovered after restart.

# quickstart

Three ways in — they all drive the same engine. These examples pin the supported v0.4.2 release; see Deployment for installation and runtime settings.

Writing a broker-only Go application? The official MQLite Remote Client for Go (mqlite-go) is standard-library-only and keeps a Go 1.13 source floor: go get github.com/mqlitehq/mqlite-go@v0.1.1. Use the full SDK below for embedded queues, transactional outbox, observation, or managed access-key administration.

No server at all: one import, one file — the queue lives inside your process. go get github.com/mqlitehq/mqlite@v0.4.2 (Go ≥ 1.21).

package main

import (
    "context"
    "fmt"
    "log"
    "time"

    "github.com/mqlitehq/mqlite"
)

func main() {
    ctx := context.Background()
    mq, err := mqlite.OpenEmbedded(ctx, "file:./mq.db")
    if err != nil {
        log.Fatal(err)
    }
    defer mq.Close()

    if err := mq.CreateQueue(ctx, "orders", mqlite.QueueConfig{
        LockDuration:     30 * time.Second,
        MaxDeliveryCount: 5,
    }); err != nil {
        log.Fatal(err)
    }

    // produce
    if _, err := mq.SendOne(ctx, "orders", mqlite.OutMessage{Body: []byte(`{"id":42}`)}); err != nil {
        log.Fatal(err)
    }

    // consume (Peek-Lock): receive, do work, then settle
    msgs, err := mq.Receive(ctx, "orders", mqlite.RecvOpts{Max: 10, Wait: 5 * time.Second})
    if err != nil {
        log.Fatal(err)
    }
    for _, m := range msgs {
        fmt.Printf("got: %s\n", m.Body)
        // Abandon retries below max (DLQ at max); Reject sends directly to DLQ.
        if err := m.Complete(ctx); err != nil {
            log.Fatal(err)
        }
    }
}

One tiny process, secure by default: it generates a mqk_… token and prints it if you don't set one. Every operation is one POST.

The supported v0.4.2 release uses port 6754 and schema token 7. It is a same-schema patch over v0.4.1, so that upgrade needs no database rebuild. Schema-5 databases from v0.3.x still require preserving the matching old binary/database pair and starting v0.4.2 with a fresh database. v0.3.3 is withdrawn and unsupported; its public artifacts remain only for forensic or compatibility inspection and must not be deployed.

go install github.com/mqlitehq/mqlite/cmd/mqlite@v0.4.2   # default port 6754

# start the broker on :6754 with a known token, in the background
MQLITE_TOKENS=mqk_dev MQLITE_DB=file:./mq.db mqlite serve &
export TOKEN=mqk_dev        # (omit MQLITE_TOKENS to have the broker generate + print one)

# create a queue, send, receive — curl-able by construction
curl -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     --data '{"name":"orders","config":{}}' \
     localhost:6754/mqlite.v1.AdminService/CreateQueue

curl -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     --data "{\"queue\":\"orders\",\"messages\":[{\"body\":\"$(printf hi | base64)\"}]}" \
     localhost:6754/mqlite.v1.QueueService/Send

curl -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     --data '{"queue":"orders","max_messages":1,"wait_time_ms":5000}' \
     localhost:6754/mqlite.v1.QueueService/Receive

A named volume keeps queue data across container replacement. The admin console is available at /ui; in v0.4.2, opening the root URL in a browser enters that console while curl and JSON clients keep the discovery card. The console groups subscriptions by topic and shows permanent or fixed lifetimes against the broker clock; its five-second loop calls only Observe, while lifecycle inventory refreshes on connection, explicit refresh and configuration changes.

# run it in production

Start with one broker over a persistent local SQLite file. Choose a durability setting and rehearse recovery before putting messages into production.

Prometheus collection is off by default. Enable --metrics or MQLITE_METRICS=on to serve authenticated /metrics on the API port, and give the collector a separate MQLITE_MONITOR_TOKENS credential. Keep collection on a private network; if the API has public ingress, deny /metrics there. v0.4.0 removes the deprecated mqlite_queue_total and mqlite_queue_oldest_message_age_ms aliases; use mqlite_queue_retained_messages and mqlite_queue_oldest_message_age_seconds. The starter includes Prometheus, Grafana, a dashboard and verification scenarios.
