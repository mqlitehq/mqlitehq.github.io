# mqlitehq.github.io

The documentation site for [mqlite](https://github.com/mqlitehq/mqlite) — plain static
HTML, no framework, no build step to *serve* (the repo root is the site root).

Public documentation: **https://mqlitehq.github.io/**. The site tracks `mqlite/main`,
including changes not yet released; use the version labels and release notes to
choose documentation matching an installed binary.

## Syncing with the code (the anti-rot rule)

Generated pages carry separate **source version** and **latest recorded release**
stamps and must never be edited by hand. The source version comes from
`internal/version/version.go`; the latest release comes from the first dated
release heading in `CHANGELOG.md`, never from the source version constant.
The website describes `main`, including changes not yet released.

Use Node 24 LTS. Whenever the mqlite docs change (and on every release):

```bash
cd tools
npm ci
node build.mjs                     # expects mqlite as the site's sibling checkout
node --test build.test.mjs
node build.mjs --check             # compares every generated byte, without writing
```

To preview a candidate, pass its absolute checkout path to both build commands.
Before committing, regenerate against the canonical checkout after its docs merge.
`--check` covers every output in `GENERATED_FILES`, including new/missing pages,
metadata, the complete LLM bundle and the vendored highlighter; tests pin that
entire inventory and verify rejection of stale content. It also checks every
advertised route/tool/command count against the source, not just one matching
mention, and verifies local links, assets and page anchors. Update hand-written
release facts deliberately when a new release lands.

Generated pages preserve the Markdown's ASCII figures directly. Keyword-based SVG
replacement is intentionally absent, so a source diagram change is immediately
visible. Keep optional SVG illustrations consistent when editing them.

## Publishing

CI runs tests and a read-only comparison on Node 24, then packages only the static
pages, public assets, machine-readable docs and metadata. Source checkouts,
generator dependencies and repository files are excluded from the Pages artifact.

Pull requests validate and package the site without deploying it. A successful
`main` push (or manual run on `main`) deploys the checked artifact through the
`github-pages` environment. Only that job receives `pages: write` and
`id-token: write`; repository contents remain read-only. Enable GitHub Pages with
**GitHub Actions** as its publishing source. The full workflow contract is pinned
in `tools/site-workflow.golden.yml` and must be deliberately updated when changed.

To inspect the same static artifact locally, use a new output directory:

```bash
sh tools/package-site.sh /absolute/path/to/new/site-output
```

Content rules: English only; distinguish main from released behavior, cite
`docs/benchmark.md` for measured numbers, and keep the "when NOT to use" section
honest.
