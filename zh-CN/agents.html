# 面向 AI 智能体的 mqlite

mqlite 的设计让模型能够 准确使用：每项操作均为携带 JSON 正文的单次 HTTP POST，每种结算结果只有一个动词，没有会让模型困惑的别名； GET / 返回机器可读的发现卡片，投递语义则以可测试的不变量记录。以下三种使用方式按推荐程度排列。

# 1 · MCP 服务端（推荐）

mqlite-mcp 随同一个仓库提供，是无需依赖的 stdio MCP 服务端，将每次工具调用转换为发往 broker 的一次 HTTP POST。

用一条命令一起安装最新发布的 broker 与 MCP 服务端：

go install github.com/mqlitehq/mqlite/cmd/mqlite@latest github.com/mqlitehq/mqlite/cmd/mqlite-mcp@latest

两个软件包会解析为同一模块版本。运行 mqlite version 来检查 broker 二进制程序的版本；MCP 主机读取 serverInfo.version ，该字段位于 initialize响应中。已有的 broker 通过以下入口报告版本： GET /。使用匹配的版本及该版本文档；需要可复现部署时，应记录确切版本。也可从这里下载同一发布版本的两个二进制程序： 最新发布归档。接着将安装的 MCP 二进制程序注册到主机：

{
  "mcpServers": {
    "mqlite": {
      "command": "/path/to/mqlite-mcp",
      "env": {
        "MQLITE_ENDPOINT": "https://your-broker.example.com",
        "MQLITE_TOKEN": "mqk_..."
      }
    }
  }
}

当前文档对应的源码提供 22 个工具， 29 条路由 和 26 条命令。下表以该源码为准；已发布的二进制可能不包含 main 中尚未发布的变更。请确保 broker 和 mqlite-mcp 来自同一发布版本。 observe 工具要求 broker 与 MCP 服务端均为 v0.3.2 或更高版本。密钥管理工具要求 v0.3.1 或更高版本：

工具功能
list_queues列出普通队列与订阅后备队列，包括正在删除的名称
create_queue按名称创建或更新队列
delete_queue删除空的普通队列；也可显式使用 force 以丢弃保留工作
subscribe创建订阅或更新其过滤器；可选的 ttl_ms 设定一次固定生命周期
list_subscriptions按主题分页列出订阅，包含计数、生命周期状态，并可包含正在删除的条目
delete_subscription删除一个准确的 topic/name 组合；可选的 force 会丢弃所有保留工作
send发送消息（queue， body，可选 message_id / group_id）
receive按 Peek-Lock 接收消息 → 返回 seq_number + lock_token
complete / abandon / reject结算：完成 / 未达上限则重试（达到上限则进 DLQ）/ 立即转为死信
renew在到期前延长同一次有效领取； delivery_count 保持不变
defer / receive_deferred暂存后按序号领取；领取会增加 delivery_count ；目前没有最大投递次数准入检查
peek不加锁浏览，可按状态筛选
stats按状态统计队列深度
observebroker 健康状态与生命周期时钟、队列快照、消息操作效果、存储和请求测量值（自 v0.3.2 起）
redrive / purge将死信移回正常队列 / 删除死信
create_key签发密钥，包含 id， name， permissions ，以及可选的 expires_at_ms；令牌只返回一次
list_keys列出公开元数据，使用 after_id / limit / sort，包括已撤销和已过期的密钥
revoke_key撤销密钥，使用公开字段 id；重复撤销是安全的

密钥工具要求 manage；配置中的管理员和托管的 manage 密钥均可签发新的管理员密钥。请为消息生产者授予 send ，消费者使用 listen。在当前文档对应的源码中， listen 还允许在整个 broker 范围创建订阅、更新过滤器和测试过滤器；订阅清单与删除仍要求 manage，无论是否使用 force。消费者可以结算消息，也可以按接收即删除模式消费； listen 并非仅审计角色。

若 MCP 连接仅用于监控，请将配置中的 MQLITE_MONITOR_TOKENS 凭据填入客户端的 MQLITE_TOKEN。它可以调用 observe，但不能读取消息正文、消费消息、修改队列或签发密钥。请检查返回的采集状态和可用性字段；不可用的测量值不能视为健康的零值。v0.4.1 增加了 server_time_ms 用于比较生命周期截止时间；请勿替换为缓存的队列采样时间字段 sampled_at_ms。参见 可观测性。 observe 工具独立于可选的 Prometheus 开关工作； --metrics 仅启用经过鉴权的 /metrics 端点，位于 API 端口。v0.4.0 删除了已弃用的 mqlite_queue_total 和 mqlite_queue_oldest_message_age_ms 别名；请使用 mqlite_queue_retained_messages 和 mqlite_queue_oldest_message_age_seconds。

创建生产者密钥

调用工具前，先选择并保留一个唯一的公开 ID，由 32 位小写十六进制字符组成：

{
  "name": "create_key",
  "arguments": {
    "id": "e734810a9f634d75bd8a029c1f7e5062",
    "name": "orders-producer",
    "permissions": ["send"]
  }
}

请妥善保管返回的 mqk_ 加 64 位小写十六进制字符组成的令牌；令牌只在工具结果中显示一次，MCP 宿主可能保留该结果。请保留公开 ID，用于列举和撤销。若创建响应丢失，先根据该 ID 核对状态，并在签发另一把密钥前撤销可能已经创建的密钥；用同一 ID 重试无法找回秘密令牌。使用 next_after_id 遍历 list_keys 的各页结果完成分页。参见 访问密钥 了解过期、轮换与恢复。

列表默认使用 sort: "id_asc"。使用 sort: "created_desc" 按最新创建的密钥优先排序；时间戳相同时，按公开 ID 降序排列。每页必须沿用同一排序方式。按创建顺序分页时，游标必须指向现有密钥。默认 ID 排序还接受不存在的前驱 ID，以便核对响应丢失的创建请求。

详情： docs/mcp.md。

# 2 · 原始 HTTP：可直接粘贴的提示词

适用于能运行 curl 或发起 HTTP 调用的智能体。这份提示词以当前文档对应的源码 API 为准。请核对已部署 broker 的版本和服务发现信息；已发布二进制应使用对应发布版本的文档，未发布二进制则应使用该构建自身的源码文档。填写两个占位符后，将匹配的说明粘贴到智能体的系统提示词或任务上下文中：

你可以访问一个消息队列（mqlite broker）。

基础 URL： <MQLITE_ENDPOINT>              broker 的源地址，包含端口。
           直连： http://127.0.0.1:6754   （示例：broker 已配置在 TCP 6754 端口，
                                             自身不终止 TLS）
           代理： https://mq.example.com  （反向代理在 HTTPS :443 接收请求，
                                             再转发到 broker 内部的 :6754）
           下文端点路径均相对于此源地址。
认证：     每次 RPC 调用都需要请求头            Authorization: Bearer <MQLITE_TOKEN>
协议：     每个操作都是一次携带 JSON 请求体的 HTTP POST，目标为
           /mqlite.v1.QueueService/<Method>、/mqlite.v1.AdminService/<Method>，
           或 /mqlite.v1.AuthService/<Method>（v0.3.1 及后续版本）。
           GET / 携带 Accept: application/json（无需认证）返回服务发现信息，
           其中包含 broker 版本和全部端点。

规则：
- 更改数据前先 GET /，携带 Accept: application/json，读取其 version 和端点清单。
  仅使用部署中的 broker
  已记录的 API。已发布二进制应使用其精确发布标签的文档；未发布构建
  应使用该构建自身的源码文档。
- 密钥权限：send 允许生产/定时发送/取消消息；listen 允许接收/结算/续锁/查看消息、
  读取队列统计、创建或更新订阅，以及测试过滤条件；manage
  包含上述两类权限，以及管理/签发密钥。查看订阅清单和每一次
  DeleteSubscription 请求都要求 manage，无论 force 为 false 还是 true。
  权限适用于整个 broker。不要重试 401 或 403；应向管理员获取
  具备所需权限的有效密钥。
- v0.3.2+ 中，AdminService/Observe {} 可使用配置的
  monitor 凭据或 manage 密钥读取 broker 测量值。应检查 collection/availability 字段；缺失的
  测量值不等于零。监控凭据不能读取消息体。
- JSON 中的消息体是 BASE64 字符串。发送前编码，
  接收后解码。
- 队列绝不会自动创建。请先创建：
    AdminService/CreateQueue  {"name":"jobs","config":{}}
  队列和订阅删除默认仅允许空资源。force=true 是显式
  授权，允许丢弃所有保留状态，包括持锁处理中的消息。成功的
  state=deleted 结果表示清理已在接受请求的提交中完成；state=deleting
  表示有界清理仍在继续，并且名称仍被保留。API 没有 Generation
  字段：必须由一个所有者核对清单，并将删除与同名
  创建串行协调。遇到重定向、传输失败、任意 5xx 或无效的成功响应体后，
  不要重试删除。应使用 ListQueues 或 ListSubscriptionsPage，配合
  include_deleting=true 核对；在单一所有者规则下，名称不存在即可确认清理完成。
- 使用 Peek-Lock 消费：
    QueueService/Receive  {"queue":"jobs","max_messages":1,"wait_time_ms":5000}
  每次新授予的 Peek-Lock 领取都会增加 delivery_count。返回的每条
  消息都包含 seq_number + lock_token。你必须结算收到的每条消息，
  使用它的 lock_token：
    QueueService/Complete {"queue":"jobs","seq_number":N,"lock_token":"..."}  完成
    QueueService/Abandon  {...,"delay_ms":60000}   未达上限则重试；达到上限 -> DLQ
    QueueService/Reject   {...}                    放弃处理 -> 死信队列
  如果不结算，锁会过期（默认 30s）。恢复处理会将
  消息移回 active，或在最后一次尝试失败后将其送入 DLQ。达到
  上限不会中断最后一次领取：它仍可续锁或完成。
  新的结算和 Renew 要求 locked_until_ms > now：恰好到达截止时间
  就已过期，即使回收器尚未运行也一样。未过期回执只允许
  完全相同的请求在租约到期后重放之前已提交的结算。
- Receive-and-Delete 是显式的至多一次 broker 移除语义，不授予租约：
  lock_token 为空，locked_until_ms 为零（JSON 中省略），包括
  receive-attempt 重放。不要对它执行结算。
- 默认 Peek-Lock 投递为至少一次（AT-LEAST-ONCE）：你可能两次看到同一条消息。
  应通过自己持久化的状态确保业务处理幂等。仅设置 message_id
  不会对发送去重：重复检测默认关闭。队列
  设置了正数 dedup_window_ms 时，应在该保留窗口内使用相同的 message_id 和消息体
  重试；消息体不同则发生冲突。broker 去重不能让
  外部副作用变成恰好一次。
- 长时间处理：在租约过期前，携带 lock_token 调用 QueueService/Renew。
  它延长同一次领取，不增加 delivery_count，不累加
  时长，也无法恢复已经过期的租约。
- 发布/订阅：AdminService/Subscribe {"topic":"events","name":"my-sub",
  "filter":{"expr":"subject == \"order\""},"ttl_ms":900000} —— 随后向
  "events" 执行 Send 会进行扇出；从 "my-sub" 执行 Receive。filter 可省略；省略 ttl_ms 或设为零
  会创建永久订阅，或保留现有存活期。
  正数 TTL 是从首次创建起计算的固定存活期：重试、过滤条件更新
  和消息流量都不会延长它。到期意味着已预先授权强制清理。
  正常使用结束后应显式删除；高频请求/回复应使用一个稳定回复
  订阅，并按 correlation_id 分发，而不是每次请求创建一个订阅。
  Subscribe 和 TestFilter 要求 listen；列出和删除订阅要求
  manage。Subscribe 是整个 broker 范围的创建或更新操作，不代表仅创建或调用方专属所有权。
- 有序处理：发送时提供 "group_id"——具有相同 group_id 的消息
  严格按顺序投递，每组同一时刻仅一条在途消息。delay_ms > 0 的 Abandon
  将消息暂放在 scheduled 状态，并继续阻塞其有序分组，直至预定重试时刻
  （strict_fifo：阻塞整个队列）。Cancel 只移除从未投递过的定时
  消息，即 delivery_count = 0。
- 消息 TTL：整个 Send 批次的存活期相同时，使用顶层 ttl_ms；
  各条目存活期不同时，使用 messages[].ttl_ms。正数队列默认值同时是默认值和
  上限。固定的 expires_at_ms 等于初始 visible_at_ms + 生效的 TTL，因此
  定时消息从首次到达预定投递时间开始计算 TTL。Renew、延迟 Abandon 和
  调度器激活都不会延长它。到期后终止正常投递，再
  根据队列策略进入死信或被丢弃。
- 错误采用 JSON {"code","message"}：400 invalid_argument · 401 unauthenticated ·
  403 permission_denied · 404 not_found ·
  409 name_conflict / already_exists / lock_lost / key_conflict /
      queue_not_empty / subscription_not_empty ·
  413 message_too_large · 429 resource_exhausted · 503 outcome_unknown。
  遇到 409 lock_lost，应重新执行 Receive，而不是重试结算。503
  outcome_unknown 可能已经提交；应核对结果，而不是盲目重试。
  精确结算回执从记录时起保留 30 分钟；重放不会延长
  窗口，资源删除或到期可能使重放提前结束。如果核对结果需要超出
  该窗口，应保留应用侧证据。

速查表（请求体已简写）：
  AdminService/CreateQueue   {"name","config":{}}
  AdminService/DeleteQueue   {"name","force?"}
  AdminService/ListQueues    {}
  AdminService/Subscribe     {"topic","name","filter?","ttl_ms?"}
  AdminService/TestFilter    {"expr","message?"}
  AdminService/ListSubscriptionsPage {"topic?","after?","limit?","include_deleting?"}
  AdminService/DeleteSubscription {"topic","name","force?"}
  QueueService/Send          {"queue","messages":[{"body":"<base64>",
                              "message_id?","group_id?"}]}
  QueueService/Receive       {"queue","max_messages","wait_time_ms"}
  QueueService/Complete      {"queue","seq_number","lock_token"}
  QueueService/Abandon       {"queue","seq_number","lock_token","delay_ms?"}
  QueueService/Reject        {"queue","seq_number","lock_token"}
  QueueService/Renew         {"queue","seq_number","lock_token"}
  QueueService/Stats         {"queue"}
  AuthService/CreateKey      {"id","name","permissions":["send"],"expires_at_ms?"}
  AuthService/ListKeys       {"after_id?","limit?","sort?"}
  AuthService/RevokeKey      {"id"}
  对 CreateKey：调用前先保留一个唯一的 32 字符小写十六进制 id。token
  仅返回一次。结果不确定时，先列出/撤销该 id，再创建替代密钥；
  重复 id 会返回 key_conflict，绝不会再次返回秘密值。
  对 ListKeys：sort 默认为 id_asc。使用 created_desc 可按最新优先排列，
  每页保持相同 sort，并将 next_after_id 作为 after_id 传回。
API 参考：https://mqlitehq.github.io/api.html
对于已发布的 broker，应使用其已安装版本的参考文档，
不要假定尚未发布的 main 行为已经可用。
为什么适合模型使用： 无需管理连接状态，无二进制协议，也无需安装 SDK；每一步都是独立的 POST，响应明确告诉模型下一步应使用哪个令牌。若结算响应丢失，只要回执未过期，就可以安全重试，方法是 重发同一个请求：队列、消息、锁令牌、操作动词以及会改变效果的参数均保持一致。改变这组身份，就会得到 lock_lost，绝不会悄然保留首次调用的效果却返回成功。有效回执可在原租约到期后重放已提交的结算，但不能授权新效果，也不能恢复租约。因此，智能体即使弄错了请求，也会得到明确错误，而不会悄悄执行错误操作。

# 最重要的一条规则

默认的 Peek-Lock 投递仅承诺 至少一次（at-least-once）；显式的接收即删除模式则选择在 broker 侧至多删除一次（at-most-once）。broker 无法保证 handler 的外部副作用恰好发生一次。设计智能体工作流时，应确保 同一消息处理两次也无害：以 message_id 或自己的幂等键标识副作用，并及时结算。其他规则请参阅 核心概念页面。
