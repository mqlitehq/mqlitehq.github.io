mqlite

消息队列，存储于 单个 SQLite 文件。

Peek-Lock 投递、重试、死信队列、调度、去重、FIFO 分组和主题扇出： 嵌入 Go 进程 或运行成一个 小型 HTTP broker。同一引擎、同一文件，由你选择。

# 解决哪些问题

每个后端反复遇到的三个问题。

“我需要后台任务，不想部署 broker。”

只为一个服务，却要运维集群、学习 SDK，还要付费。
→ 一个库，基于一个文件运行

无需额外基础设施。之后需要 HTTP？同一引擎可作为约 30 MB 的单个进程运行。

“数据库写入与事件可能不一致。”

保存订单，再发布事件；两步之间崩溃就会使二者不一致。发件箱表和 CDC 又增加一层设施。
→ 两者使用同一事务

队列 就是 你的 SQLite 数据库：业务写入与入队一起原子提交。

“手写的任务表变成了一个不可靠的 broker。”

一个 status 列和轮询循环，会逐渐衍生出未经测试的锁、重试与死信机制。
→ 直接提供完整语义

Peek-Lock、重试 → DLQ 与重新投递、FIFO 分组、延迟、去重：均由一致性测试集固定其行为。

# 为什么选择 mqlite

以下为设计优先级；发生冲突时，顺序靠前的优先。

1轻量、可嵌入

一个纯 Go 二进制文件，基于一个 SQLite 文件运行。无需 broker 集群、sidecar 或 CGO。可以先嵌入进程，再将同样的代码迁至 broker，或将存储迁至具有复制能力的 Turso，无需重写应用。

2并发下可靠

默认 Peek-Lock 投递如实承诺 至少一次（at-least-once）；显式的接收即删除模式则选择在 broker 侧至多删除一次（at-most-once）。新的结算要求当前令牌和未过期租约；支持按配置启用发送去重、有界的接收与结算重放、单 broker 崩溃恢复，以及深积压下 O(log n) 的领取。即使消费者崩溃或锁到期，FIFO 组仍保持顺序。

3简单、无歧义的接口

每项操作都是 携带 JSON 正文的单次 HTTP POST ；源版本 v0.4.2 有 29 条路由，设计上均可用 curl 调用，每种结算结果只有一个动词（Complete / Abandon / Reject / Defer），没有别名。人易于使用，也方便 智能体。

4借鉴 Service Bus，保持自身设计

Peek-Lock、 group_id 会话、DLQ 与重新投递、调度和重复检测，借鉴 Azure Service Bus 的熟悉机制，并采用符合 Go 习惯的形式； 完整模型已有文档说明 ，公开的兼容性不变量由以下测试集固定： 一致性测试集。

# 核心特性：无需独立发件箱的事务发件箱

由于队列 就是 你的 SQLite 数据库，业务写入与其事件可以通过 同一事务提交。创建订单与初始队列事件一起成功或回滚，不存在双写竞态，无需 CDC 流水线或轮询器。

仅限嵌入式模式：这种方式不依赖独立 broker 或 Postgres。 外部 broker 无法参与 SQLite 事务，而基于 Postgres 的队列需要 Postgres。在这里，业务数据与队列共享同一文件。
package main

import (
    "context"
    "log"

    "github.com/mqlitehq/mqlite"
    "github.com/mqlitehq/mqlite/engine"
)

func main() {
    ctx := context.Background()
    mq, err := mqlite.OpenEmbedded(ctx, "file:./app.db")
    if err != nil {
        log.Fatal(err)
    }
    defer mq.Close()
    if err := mq.CreateQueue(ctx, "order-events", mqlite.QueueConfig{}); err != nil {
        log.Fatal(err)
    }

    err = mq.Tx(ctx, func(tx *engine.EngineTx) error {
        // Demo schema; application migrations normally create this table.
        if _, err := tx.SQL().ExecContext(tx.Context(),
            `CREATE TABLE IF NOT EXISTS orders(id INTEGER PRIMARY KEY, total INTEGER NOT NULL)`); err != nil {
            return err
        }
        // 1) the business write, on the SAME transaction. Use tx.Context(), not the
        //    ctx you passed to Tx — a statement interrupted mid-transaction wedges
        //    a local SQLite database.
        if _, err := tx.SQL().ExecContext(tx.Context(),
            `INSERT INTO orders(id, total) VALUES(?, ?)`,
            42, 1999); err != nil {
            return err // rollback: nothing enqueued
        }
        // 2) enqueue — commits atomically with it:
        _, err := tx.SendOne("order-events",
            engine.OutMessage{Body: []byte(`{"order":42}`)})
        return err
    })
    if err != nil {
        log.Fatal(err)
    }
    // A nil result confirms that the order and its event committed together.
}

示例使用一个全新的 app.db ，并仅插入一次订单 42。原子性保证业务写入与入队一起提交；它不保证外部副作用恰好发生一次，也不能证明超时的远程提交已失败。重试前请先核对不确定结果。参见 事务入队。

# 工作原理

两类投递目标，同一存储模型：主题不存储消息；负责存储、供消费并可能产生死信的，始终是队列。

  1. 01 · 发布（Publish）发布者（publisher）发布 order.created ，目标为隐式主题（implicit topic） events 。
  2. 02 · 路由主题（topic）不存储消息。两个订阅（subscription）的过滤条件（filter）均匹配该消息。
  3. 03 · 复制audit 和 fulfillment 各获得独立的支撑队列（backing queue）副本：消息 ID 相同，序号不同。
  4. 04 · 领取（Receive）每次 Receive 将对应副本从就绪（active）改为已锁定（locked），并将 delivery_count 增加到 1。
  5. 05 · 分别结算audit 完成（Complete），只删除自己的消息副本，订阅仍保留。未达到投递上限时， fulfillment 带延迟放弃（Abandon）消息，将自己的副本由已锁定（locked）移至待调度（scheduled），不增加投递计数。
  6. 06 · 到期可用调度器将延迟副本恢复为就绪（active），其投递计数仍为 1。
  7. 07 · 重试下一次 Receive 将副本置为已锁定（locked），并将 delivery_count 增加到 2。
  8. 08 · 完成（Complete）重试完成（Complete）后，这份消息副本也被删除；两个订阅都仍保留。投递为至少一次（at-least-once），因此消息处理函数（handler）必须保持幂等。

动画时序仅作演示，不代表 broker 延迟。即使达到投递次数上限，最后一次普通领取仍可续锁和完成。只有显式拒绝，或最后这次锁被放弃、到期或显式回收，消息才进入 DLQ。未发布的 main 在普通打开时保留未过期租约；v0.4.2 启动时仍会回收这些租约。参见 关停与重启边界。

# 快速入门

三种使用方式，驱动同一引擎。以下示例固定使用受支持的 v0.4.2；参见 部署 了解安装与运行时设置。

只连接 broker 的 Go 应用？官方的 MQLite Go 远程客户端（mqlite-go） 仅依赖标准库，源码最低要求为 Go 1.13： go get github.com/mqlitehq/mqlite-go@v0.1.1。若需要嵌入式队列、事务发件箱、观测功能或托管访问密钥管理，请使用下方的完整 SDK。

完全无需服务端：引入一个包，使用一个文件，队列就运行在你的进程内。 go get github.com/mqlitehq/mqlite@v0.4.2 （Go ≥ 1.21）。

package main

import (
    "context"
    "fmt"
    "log"
    "time"

    "github.com/mqlitehq/mqlite"
)

func main() {
    ctx := context.Background()
    mq, err := mqlite.OpenEmbedded(ctx, "file:./mq.db")
    if err != nil {
        log.Fatal(err)
    }
    defer mq.Close()

    if err := mq.CreateQueue(ctx, "orders", mqlite.QueueConfig{
        LockDuration:     30 * time.Second,
        MaxDeliveryCount: 5,
    }); err != nil {
        log.Fatal(err)
    }

    // produce
    if _, err := mq.SendOne(ctx, "orders", mqlite.OutMessage{Body: []byte(`{"id":42}`)}); err != nil {
        log.Fatal(err)
    }

    // consume (Peek-Lock): receive, do work, then settle
    msgs, err := mq.Receive(ctx, "orders", mqlite.RecvOpts{Max: 10, Wait: 5 * time.Second})
    if err != nil {
        log.Fatal(err)
    }
    for _, m := range msgs {
        fmt.Printf("got: %s\n", m.Body)
        // Abandon retries below max (DLQ at max); Reject sends directly to DLQ.
        if err := m.Complete(ctx); err != nil {
            log.Fatal(err)
        }
    }
}

一个小进程，默认安全：若未配置令牌，它会生成 mqk_… 令牌并打印。每项操作都是一次 POST。

受支持的 v0.4.2 使用端口 6754 和 schema 令牌 7。它是基于 v0.4.1 的同 schema 补丁版本，因此此次升级无需重建数据库。对于 v0.3.x 的 schema-5 数据库，仍需保留配套的旧二进制与数据库，并让 v0.4.2 使用全新数据库启动。v0.3.3 已撤回且不再受支持；公开产物仅供取证或兼容性检查，不得部署。

go install github.com/mqlitehq/mqlite/cmd/mqlite@v0.4.2   # default port 6754

# start the broker on :6754 with a known token, in the background
MQLITE_TOKENS=mqk_dev MQLITE_DB=file:./mq.db mqlite serve &
export TOKEN=mqk_dev        # (omit MQLITE_TOKENS to have the broker generate + print one)

# create a queue, send, receive — curl-able by construction
curl -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     --data '{"name":"orders","config":{}}' \
     localhost:6754/mqlite.v1.AdminService/CreateQueue

curl -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     --data "{\"queue\":\"orders\",\"messages\":[{\"body\":\"$(printf hi | base64)\"}]}" \
     localhost:6754/mqlite.v1.QueueService/Send

curl -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     --data '{"queue":"orders","max_messages":1,"wait_time_ms":5000}' \
     localhost:6754/mqlite.v1.QueueService/Receive

命名卷会在容器替换后保留队列数据。管理控制台位于 /ui；在 v0.4.2 中，用浏览器打开根 URL 会进入该控制台，而 curl 和 JSON 客户端仍收到发现卡片。控制台按主题分组显示订阅，并以 broker 时钟展示永久或固定生命周期；每五秒的循环仅调用 Observe；生命周期清单则在连接、显式刷新和配置变更时更新。
